# Критерии полноты спеки

← [Правила](README.md) · [SDD](sdd.md)

Спека — контракт поведения. Чек-лист применяют при написании (роль «автор критериев») и при ревью. Неприменимый пункт — объяснить, а не пропускать.

## 0. Основа

| Методология | Что даёт спеке |
|---|---|
| Формат спек (OpenSpec) | Purpose, дельты требований, SHALL / MUST, сценарии WHEN / THEN |
| **ISO/IEC/IEEE 29148** | 9 характеристик требования: необходимое, однозначное, полное, единичное, реализуемое, проверяемое, корректное, соответствующее, трассируемое; 5 характеристик набора: полный, согласованный, реализуемый, понятный, ограниченный |
| **Трассировка (RTM)** | требование трассируется вверх (история, исследование, решение) и вниз (задача, тест) |
| **User Stories + BPMN** | требования выводятся из историй и процессов, включая ветки ошибок |
| **Software FMEA** | режимы отказа: требования, интерфейсы, данные, тайминги, последовательность, обработка ошибок |
| **Классы сценариев S1–S12** (эквивалентные классы и границы тест-дизайна) | покрытие поведения, а не только основного пути |
| **ISO/IEC 25010 — эффективность** | профиль нагрузки, время ответа, ёмкость |
| **C4 / arc42 — развёртывание** | где и как запущен модуль |
| **EARS, Spec Kit** ([SDD](sdd.md)) | шаблоны текста и цепочка constitution → specify → plan → tasks |
| **Персоны и отыгрыш конфликтов** | конфликты разыгрываются по промптам персон → истории, требования, вопросы |
| **Ревью по ролям** | вопросы в разных разрезах ([роли](roles.md)) |

## 1. Формат

- [ ] `## Purpose` — 1–2 предложения, ≥ 50 символов, в конце «Обоснование: ссылка на R&D»
- [ ] Дельты — `## ADDED / MODIFIED / REMOVED / RENAMED Requirements` (если формат с дельтами)
- [ ] Требование — `### Requirement: <имя>`, одно поведение, описание ≤ 500 символов, **SHALL / MUST**
- [ ] Сценарии — `#### Scenario:`, формат **WHEN / THEN**
- [ ] MODIFIED — блок целиком; REMOVED — с **Reason** и **Migration**
- [ ] Нет имён классов и шагов реализации (это решения и задачи)

## 2. Покрытие сценариев (≥ 3 на требование)

| # | Класс | Вопрос |
|---|---|---|
| S1 | Основной путь | Нормальный вход? |
| S2 | Альтернативный путь | Другие допустимые ветки? |
| S3 | Неверный вход | Ошибочные или отсутствующие данные? |
| S4 | Границы и лимиты | На пороге и сразу за ним? |
| S5 | Права и безопасность | Кто может / не может, секреты? |
| S6 | Сбой зависимости | Сервис недоступен, таймаут? |
| S7 | Параллельность | Одновременные запросы, гонки? |
| S8 | Повтор и идемпотентность | Повторная отправка, дубли? |
| S9 | Конфигурация | Включено / выключено, другие значения? |
| S10 | Состояние и восстановление | Падение посреди процесса? |
| S11 | Данные и хранение | Срок хранения, удаление, приватность? |
| S12 | Наблюдаемость и аудит | Видно ли, что и почему произошло? |

## 3. Обязательные части спеки

| Файл | Содержание |
|---|---|
| `spec.md` | требования и сценарии |
| `architecture.md` | схема устройства, блоки, расширения, плюсы / минусы ([формат схем](diagrams.md)) |
| `interfaces.md` | уровни конфигурации; [параметры](sdd.md#params); хранилища (S-коды: что, владелец, бэкап / срок); интерфейсы (I-коды: от → к, протокол, формат, аутентификация, режим, таймаут, повтор, идемпотентность); FMEA (отказ, обнаружение, поведение, восстановление); нагрузка и развёртывание |
| `traceability.md` | требование → обоснование → задача → число сценариев; разрывы явно |
| `open-questions.md` | ID, вопрос, ❓ / 📌, блокирует ли, источник, кто решает |
| `approvals.md` | подтверждения требований ролями |

Обязательные требования в `spec.md` — **со своим содержанием** спеки, не шаблонным текстом:

- [ ] **Конфигурация** — по [виду спеки](sdd.md#kinds)
- [ ] **Хранилища данных** — только перечисленные хранилища, чужие данные через API, секреты не в БД / git
- [ ] **Интерфейсы обмена** — протокол, таймаут, повтор; неидемпотентное не повторяется
- [ ] **Поведение при отказах** — строка FMEA и сценарий отказа говорят одно и то же (меняешь одно — меняешь другое в той же правке); не меньше трёх сценариев
- [ ] **Нагрузка и производительность** — показатели профиля нагрузки, поведение при превышении
- [ ] **Развёртывание** — где, как, реплики, ресурсы, вход
- [ ] Текст — по EARS; отказы — IF … THEN

Коды S и I — единые для всех спек.

## 4. Дополнения для агентных систем

- [ ] **Quality gate** — отдельное требование со сценариями «прошёл / не прошёл», если результат проверяется
- [ ] **Уровень автономии** для действий с подтверждением человека
- [ ] **«98/2»** — детерминированные проверки описаны как проверки кодом, не LLM
- [ ] **Трассировка** — у каждого требования задача (или «не в MVP»)

## 5. Связность

- [ ] Не противоречит архитектуре и решениям
- [ ] Каждое требование выводится из истории (или помечено «техническое»)
- [ ] Процессы: у шагов указаны артефакты; конфликты персон отыграны
- [ ] У требования ID и задача; задача ссылается обратно ([трассировка](change-process.md#req-task-trace))
- [ ] Каждое открытое замечание ревью — в вопросах спеки
- [ ] Таблица параметров: по умолчанию с обоснованием, мин, макс, на что опираться
- [ ] Обязательные роли подтвердили требования
- [ ] Для каждого хранилища и вида данных: кто пишет, кто читает, кто удаляет, по какому триггеру
- [ ] Значение параметра — в одном месте
- [ ] FMEA: строка на каждое своё хранилище и каждый интерфейс
- [ ] Интерфейсы внешних систем сверены с их кодом или документацией (источник указан)
- [ ] Механизм описан даже при открытом решении о варианте (вариант — открытым вопросом)
- [ ] Связующее описано во всех спеках-участниках ([правило](change-process.md#cross-spec))
- [ ] Спека привязана к компоненту; у компонента есть «Как работает»

## 6. Процент готовности

Считается проверкой и показывается на странице спеки. Измеримый минимум, а не доказательство полноты.

| Часть | Вес | Как считается |
|---|---|---|
| Формат | 15 | Purpose ≥ 50 (4), SHALL / MUST у всех (4), сценарии у всех (4), описание ≤ 500 (3) |
| Сценарии | 25 | среднее min(сценариев, 3) / 3 |
| Трассировка | 20 | доля требований с **двусторонней** связью с задачей (или «бэклог») |
| Обоснование | 10 | в Purpose (5), в RTM (5) |
| Интерфейсы, отказы, нагрузка | 15 | разделы `interfaces.md`, требование об отказах с ≥ 3 сценариями, требования о нагрузке и развёртывании |
| Связность | 15 | схема рядом (5), привязка к компоненту (5), «Как работает» (5) |
| Открытые вопросы | минус | ❓ −2 (не более −10), 📌 −4 (не более −16) |
| Шаблонный текст | минус | −2 за требование, совпадающее с требованием другой спеки > 80% (триграммы слов), не более −10 |
| Без истории | минус | −2 за «техническое» требование, где есть пользователь, экран, уведомление (кроме сквозных), не более −10 |
| Потолок без ревью | потолок | пока в ревью есть открытые ❓ / 📌 по спеке — не выше 90 |
| Потолок без подтверждений | потолок | пока есть обязательные подтверждения ⏳ или ❌ — не выше 90 |

| Шкала | 90–100 | 75–89 | 60–74 | 40–59 | 0–39 |
|---|---|---|---|---|---|
| Статус | готова | почти | в работе | черновик | заготовка |

**Достаточность:** готовность ≥ 90, в RTM нет разрывов без решения, ревью тремя ролями не оставило вопросов уровня «блокирует реализацию».

## 7. Готовность к ревью

- [ ] Валидация формата без ошибок
- [ ] Проверки проекта зелёные
- [ ] Разделы 1–5 пройдены, неприменимое объяснено
