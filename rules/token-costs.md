# Расход токенов

← [Правила](README.md) · [подтверждения](approvals.md#economy) · [процесс изменения](change-process.md) · [данные](data.md#yaml)

Сколько токенов уходит на единицу работы по процессам методологии — **ожидание против замера**. Цель — дешёвые процессы: всё, что можно, делают скрипты, проверки и сценарии, а не LLM; агент работает с компактными машиночитаемыми данными, полные документы перегенерируются один раз в конце.

## Журнал и страница проекта

| Что | Где | Команда |
|---|---|---|
| Журнал замеров | `data/costs.yaml` проекта (`[costs] file` конфига; YAML или JSON) — запись: дата, процесс (код латиницей), методология (`файл#якорь` в правилах), единиц, единица, токенов, модель, минут, ожидание `[мин, макс]` на единицу, примечание | `cost add <процесс> <токены> <единиц> <единица> [--method файл#якорь] [--expect a-b] [--model M] [--min N] [--note …]` |
| Сводка | последний замер каждого процесса на единицу против ожидания, статус | `cost` |
| Страница проекта | генерируется из журнала (`[costs] page`): сводка и замеры по процессам; руками не правится, `check` ловит отставание от журнала | `cost md` (и сам `cost add`) |

Вручную: строка журнала по тем же полям; статус — по допуску ниже. Пример журнала и сгенерированной страницы — [examples/minimal](../examples/minimal/token-costs.md) (записи-образцы).

В методологиях, у которых есть процессы, — строка «Расход: см. …» со ссылкой на якорь процесса здесь; цифры ожидания живут только в журнале, в методологиях не повторяются.

<a id="measure"></a>

## Как замерять
1. Расход агента — токены из его отчёта о завершении (у Claude Code — `subagent_tokens`); делить на число единиц работы: пара «документ × роль», документ, компонент, файл, замечание.
2. Главный контекст оркестратора не смешивается с расходом агентов: при необходимости — отдельной записью с пометкой «оценка».
3. Прерванные запуски в замер не входят; если известен только расход завершённых частей — так и написать в примечании.
4. **Допуск ±2×:** замер на единицу от половины минимума до удвоенного максимума ожидания — ✅; иначе ⚠️ «расхождение >2×» — **остановиться и разобрать** причину до следующего прогона: правится ожидание (оно было неверным) или процесс (он стал дороже: читает лишнее, повторяет проверки, не пользуется инструментом).
5. Новый процесс — с `--method` (методология и якорь) и `--expect` после первого разбора; дальше ожидание наследуется от предыдущей записи процесса.

## Ориентиры по процессам

Пример замера одного проекта (Opus / Sonnet, 2026); у вашего проекта цифры свои — заводите их в журнал после первых прогонов.

<a id="review-batch"></a>

### Пакетная проверка ролями
`review-batch` → один JSON → `approve-batch` ([правило](approvals.md#economy)): **~1–1,5 тыс. токенов на документ** за все его роли; ориентир: **~1,4 тыс. на документ при пачке 40 страниц** агентом без тяжёлых инструментов.

<a id="review-pack"></a>

### Проверка пакетом на роль (запасной режим)
`review-pack` на каждую пару: ~4–7 тыс. токенов на пару «документ × роль» — в 10–20 раз дороже пачки на документ с несколькими ролями.

<a id="unit-read"></a>

### Чтение единицы данных
`unit <ID>`: ~250 токенов на единицу против ~25 тыс. на чтение монолитного файла данных целиком ([YAML по единице](data.md#yaml)).

<a id="yaml-migration"></a>

### Перенос данных в YAML по единице
Разовый перенос монолитного файла данных: ~1 тыс. токенов на файл единицы.

<a id="bulk-edit"></a>

### Партия правок компонента
Исправление замечаний ролей партией по компоненту ([массовые изменения](change-process.md#bulk)): ~80–230 тыс. токенов на компонент.

<a id="lint-conversion"></a>

### Перевод отказов в lint
Повторяющееся замечание ролей → правило lint ([экономная проверка](approvals.md#economy)): ~1,5 тыс. токенов на замечание; дальше эти отказы стоят ноль.

<a id="rules-transfer"></a>

### Перенос правил в методологию
Правило проекта → общая методология и инструменты ([изменение правил](change-process.md#rules-change)): ~120–280 тыс. токенов на документ.
