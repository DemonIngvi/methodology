# Расход токенов

← [Правила](README.md) · [подтверждения](approvals.md#economy) · [процесс изменения](change-process.md) · [данные](data.md#yaml)

Сколько токенов уходит на единицу работы по процессам методологии — **ожидание против замера**. Цель — дешёвые процессы: всё, что можно, делают скрипты, проверки и сценарии, а не LLM; агент работает с компактными машиночитаемыми данными, полные документы перегенерируются один раз в конце.

## Журнал и страница проекта

| Что | Где | Команда |
|---|---|---|
| Журнал замеров | `data/costs.yaml` проекта (`[costs] file` конфига; YAML или JSON) — запись: дата, процесс (код латиницей), методология (`файл#якорь` в правилах), единиц, единица, токенов, модель, минут, ожидание `[мин, макс]` на единицу, примечание | `cost add <процесс> <токены> <единиц> <единица> [--method файл#якорь] [--expect a-b] [--model M] [--min N] [--note …]` |
| Сводка | последний замер каждого процесса на единицу против ожидания, статус | `cost` |
| Страница проекта | генерируется из журнала (`[costs] page`): сводка и замеры по процессам; руками не правится, `check` ловит отставание от журнала | `cost md` (и сам `cost add`) |

Вручную: строка журнала по тем же полям; статус — по допуску ниже. Пример журнала и сгенерированной страницы — [examples/minimal](../examples/minimal/token-costs.md) (записи-образцы).

В методологиях, у которых есть процессы, — строка «Расход: см. …» со ссылкой на якорь процесса здесь; цифры ожидания живут только в журнале, в методологиях не повторяются.

<a id="measure"></a>

## Как замерять
1. Расход агента — **сумма по всем вызовам модели** из его журнала: input + запись кэша + чтение кэша + output по уникальным `message.id` (`cost from-transcript <agentId>`; в журнал — `cost add <процесс> - <единиц> <единица> --agents id,id`, токены, вызовы и итоговый контекст подставятся сами). Делить на число единиц работы: пара «документ × роль», документ, компонент, файл, замечание.
2. **Не** брать токены из отчёта агента о завершении (у Claude Code — `subagent_tokens`): это итоговый контекст последнего вызова, а не расход; он занижает расход примерно в «вызовов / 2» раз (замер одного проекта: в 5–70 раз). Он хранится в поле `context` для сравнения.
3. **Расход ≈ вызовы × средний контекст.** Главные рычаги — меньше вызовов (правки скриптом за 2–5 вызовов, потолок вызовов в брифе агента) и меньший контекст (новая сессия, когда главный контекст > ~150 тыс.). Главный контекст оркестратора замеряется так же (`cost from-transcript <uuid сессии>`), отдельной записью: в длинной сессии он дороже всех агентов вместе (замер: 2 315 вызовов × ~460 тыс. = 1,07 млрд токенов, 99% — чтение кэша).
4. Прерванные запуски входят в замер (их вызовы оплачены), отмечаются в примечании.
5. **Допуск ±2×:** замер на единицу от половины минимума до удвоенного максимума ожидания — ✅; иначе ⚠️ «расхождение >2×» — **остановиться и разобрать** причину до следующего прогона: правится ожидание (оно было неверным) или процесс (он стал дороже: читает лишнее, повторяет проверки, не пользуется инструментом).
6. Новый процесс — с `--method` (методология и якорь) и `--expect` после первого разбора; дальше ожидание наследуется от предыдущей записи процесса.

## Ориентиры по процессам

Пример замера одного проекта (Opus / Sonnet, 2026) **по журналу вызовов** — сумма по всем вызовам, включая чтение кэша; у вашего проекта цифры свои — заводите их в журнал после первых прогонов. Ориентиры прежней версии были итоговым контекстом и занижали расход в 5–70 раз.

<a id="review-batch"></a>

### Пакетная проверка ролями
`review-batch` → один JSON → `approve-batch` ([правило](approvals.md#economy)): **~4–8 тыс. токенов на документ** за все его роли; пачка 40 страниц агентом без тяжёлых инструментов — **~3,7 тыс. на документ** (4 вызова). Замер одного проекта: три пачки (40 / 40 / 24 страницы), 295 пар, 19 вызовов — **~7,2 тыс. на документ**, когда каждая пара решается отдельно с собственным комментарием (~140 символов); перепроверка отказов малой пачкой — **~20 тыс. на документ** (накладные агента не делятся). Решения одним шаблонным комментарием дешевле, но негодны: `approve-batch` их отклоняет.

<a id="review-pack"></a>

### Проверка пакетом на роль (запасной режим)
`review-pack` на каждую пару: ~25–40 тыс. токенов на пару «документ × роль» — на порядок дороже пачки на документ с несколькими ролями.

<a id="unit-read"></a>

### Чтение единицы данных
`unit <ID>`: ~250 токенов на единицу против ~25 тыс. на чтение монолитного файла данных целиком ([YAML по единице](data.md#yaml)).

<a id="yaml-migration"></a>

### Перенос данных в YAML по единице
Разовый перенос монолитного файла данных: ~80 тыс. токенов на файл единицы (111 вызовов агента; дешевле — генерировать файлы одним скриптом).

<a id="bulk-edit"></a>

### Партия правок компонента
Исправление замечаний ролей партией по компоненту ([массовые изменения](change-process.md#bulk)): скрипт-патчем агента [doc-bulk-editor](../agents/doc-bulk-editor.md) — **~3–10 тыс. токенов на файл** (пилот: 145 правок в 53 файлах, 7 вызовов, 0,32 млн); правками по YAML-единицам — 1,2–3 млн на компонент (Sonnet, 46–81 вызов); агентом файл за файлом — 5–16 млн (Opus, 53–103 вызова).

<a id="lint-conversion"></a>

### Перевод отказов в lint
Повторяющееся замечание ролей → правило lint ([экономная проверка](approvals.md#economy)): ~60 тыс. токенов на замечание (60 вызовов на 128 замечаний); дальше эти отказы стоят ноль.

<a id="rules-transfer"></a>

### Перенос правил в методологию
Правило проекта → общая методология и инструменты ([изменение правил](change-process.md#rules-change)): ~2,7–13 млн токенов на документ (28–72 вызова агента).
