# Методология SDD-требований

← [Правила](README.md) · [критерии полноты спеки](spec-criteria.md) · [шаблон требования](../templates/requirement.md)

Spec-Driven Development: спецификация, а не код — источник правды; агент реализует по спеке.

## Практики

| Практика | Что берём |
|---|---|
| **OpenSpec** (или аналогичный формат спек) | дельты требований, Requirement / Scenario, SHALL / MUST, WHEN / THEN, строгая валидация |
| **GitHub Spec Kit** | цепочка: **constitution** (принципы — правила документации) → **specify** (истории, критерии приёмки, спека) → **plan** (решения, архитектура, параметры и интерфейсы) → **tasks** (задачи) |
| **EARS** (Easy Approach to Requirements Syntax) | 5 шаблонов текста требования — однозначность и проверяемость |

## Шаблоны EARS

| Тип | Шаблон | Пример |
|---|---|---|
| Всегда | Система SHALL … | Сервис SHALL вызывать модели только через шлюз |
| Событие | WHEN <событие>, система SHALL … | WHEN задача вошла в статус «в работе», система SHALL поставить запуск в очередь |
| Состояние | WHILE <состояние>, система SHALL … | WHILE запуск ждёт подтверждения, планировщик SHALL держать слот |
| Опция | WHERE <включена функция>, система SHALL … | WHERE включена проверка вызовов, сервис SHALL проверять каждый вызов |
| Нежелательное | IF <сбой>, THEN система SHALL … | IF сервис политик недоступен, THEN сервис SHALL отклонить действие |

- Одно требование — один шаблон и одно поведение (ISO/IEC/IEEE 29148, «единичное»).
- Отказы и ошибки — только **IF … THEN** (связь с FMEA).
- Переключатели конфигурации — **WHERE**.
- Сценарии — WHEN / THEN.

## Цикл

```
constitution ─▶ specify ───────────────▶ plan ──────────────────────▶ tasks ──────────▶ реализация
правила          истории + процесс       R&D → решения → архитектура   задачи (INVEST)    агент по спеке
                 → спека (EARS)          → параметры и интерфейсы       → трассировка
                 → критерии приёмки        (уровни, S, I, FMEA, нагрузка)
```

## Виды спек
**Не генерировать спеки одним шаблоном.** Сначала вид спеки: от него зависит, что такое «конфигурация», как применяется изменение и кто подтверждает. Типичная ошибка — сквозные требования (конфигурация, хранилища, отказы), сгенерированные одним текстом для сервиса, модуля в UI существующей системы и инфраструктуры: у инфраструктуры нет «модуля, который не стартует», у настроек в интерфейсе нет «потолка конфигурации деплоя».

| Вид | Что такое «конфигурация» | Как применяется изменение | Кто подтверждает конфигурацию |
|---|---|---|---|
| **Сервис** | параметры конфигурации деплоя и настроек более низких уровней (сущность, запуск) | конфиг деплоя — при перезапуске; остальные — со следующего запуска, если не сказано иное | Разработчик, DevOps-инженер |
| **Модуль существующей системы (UI, настройки сущностей)** | настройки сущностей в интерфейсе | проверка при сохранении; действует со следующего использования | Разработчик, Администратор |
| **Образ на запуск** | параметры запуска, образ закреплён по digest | новый образ — для новых запусков, активные доделываются на прежнем | Разработчик, DevOps-инженер, Инженер сборки |
| **Инфраструктура** | значения чартов и манифесты | обновление релиза с поочерёдной заменой реплик; проверка схемой значений | DevOps-инженер |

| Сквозное требование | Сервис | Модуль существующей системы | Инфраструктура |
|---|---|---|---|
| Конфигурация | по умолчанию, границы, обязательный параметр → не стартует | по умолчанию, границы, обязательные поля → проверка при сохранении | значения в схеме, закреплённые версии |
| Хранилища | свои S-коды, роль БД на схему | таблицы системы, миграции | тома, бэкапы, объектное хранилище |
| Интерфейсы | I-коды: таймауты, повторы, идемпотентность | API системы и протоколы | вход, сетевые политики |
| Отказы | FMEA зависимостей | отказ API / БД системы | отказ узла, хранилища |

## Таблица параметров
У каждого параметра — колонки: **Параметр · Что задаёт · Уровень · Хранилище · По умолчанию · Почему так по умолчанию · Мин · Макс · На что опираться при выборе**.

- «Почему так по умолчанию» — источник значения: профиль нагрузки, константа системы, лимит провайдера, принцип наименьших прав.
- «Мин» / «Макс» — допустимые границы; граница может ссылаться на другой параметр.
- «На что опираться при выборе» — какие данные смотреть, меняя значение (статистика, нагрузочный тест, лимиты провайдера).
- Значение записано **только здесь**; в профиле нагрузки и тексте — ссылка на параметр.

<a id="trust"></a>

## Граница доверия
- **Проверка вне среды, которую она ограничивает.** Всё, что ограничивает агента (allowlist инструментов, права), MUST исполняться вне его песочницы; проверка внутри — подсказка модели, а не граница.
- **Ограничение по умолчанию проверяется типовой работой.** У параметра «наименьших прав» есть сценарий типовой работы, выполнимой при этом значении; если нет — нужен отдельный путь.

## Подтверждение требований

Сгенерированное или изменённое требование принято, когда его подтвердили все обязательные роли ([подтверждения](approvals.md#requirements)).
