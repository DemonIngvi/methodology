# Процесс изменения документации

← [Правила](README.md) · [путь изменения](agent-workflow.md) · [граф связности](doc-graph.md)

Расход: см. [партия правок компонента](token-costs.md#bulk-edit), [перенос правил в методологию](token-costs.md#rules-transfer) на странице «Расход токенов».

## Шаги

1. **Определить тип** каждого затрагиваемого документа ([типы](doc-types.md)) и его методологию.
2. **Определить роль** для шага ([роли](roles.md)).
3. **Внести изменение** по правилам типа — **в источнике факта** ([таблица источников](#single-source)), а не в производном документе. Данные (компоненты, блоки, модели, таблицы, эндпоинты, интерфейсы, истории) — только в YAML по единице, [порядок ниже](#yaml-path).
4. **Синхронизировать связанные документы** по [графу](doc-graph.md) и [матрице](#sync).
5. **Проверить:** проверки проекта (`check`, валидатор формата спек; сборка — **один раз в конце пути изменений**), для спек — [критерии полноты](spec-criteria.md), ссылки и якоря без битых. Найдено расхождение — сначала [отклонение](#deviations) с причиной, затем правило **и** проверка.
6. **Отчитаться:** список изменённых файлов и что в каждом.
7. **Коммит** с описанием.

Единичное изменение идёт по [пути изменения](agent-workflow.md): документ за документом.

<a id="yaml-path"></a>

## Правка данных — YAML по единице
Сначала компактные машиночитаемые данные, полные страницы — один раз в конце ([источник данных](data.md#yaml)).

| Шаг | Команда | Вручную |
|---|---|---|
| 1. Прочитать единицу (блок, история, модель, таблица, I-код) вместо страницы и целого файла данных | `unit <ID>` | открыть файл единицы |
| 2. Править файл единицы; новая единица — новый файл | `yaml-fmt <папка>` внесёт её в `_order.yaml` | дописать имя в `_order.yaml` |
| 3. Проверить поля, типы, значения, ссылки; полноту по методологиям | `yaml-check <файл>` → `lint <компонент>` | сверить со схемой вида в конфиге, ID — поиском |
| 4. Что перегенерируется и какой документ следующий — по одному, каждый по своей методологии (повторить 1–4) | `next <файл>` | [граф](doc-graph.md) |
| 5. В конце пути — один раз: сборка страниц → проверки → коммит | сборка проекта → `check` | — |

<a id="single-source"></a>

## Один факт — один источник
Почему документы расходятся — практически всегда одна из четырёх причин:

| Причина | Пример | Чем исключается |
|---|---|---|
| **Ручная копия факта** в двух местах | список «получает / отдаёт» в данных компонента и таблица интерфейсов в спеке; JSON-пример в API и поля модели | у факта один источник; производное генерируется, а что нельзя сгенерировать — сверяется проверкой |
| **Одностороннее изменение связи** | интерфейс описан у вызывающего компонента и забыт у вызываемого | правка связующего — во все спеки-участники ([ниже](#cross-spec)), сверка обеих сторон |
| **Цепочка последствий без производных источников** | решение D изменило шаг процесса, а примеры API и модели остались прежними | в последствиях R&D и в матрице — файл данных и примеры API как обязательные цели |
| **Нет проверки или она мягкая** | ссылки проверяются в режиме «предупреждение» | новое правило вводится вместе с проверкой; правило без проверки — временное, с задачей на проверку |

Таблица «факт → источник» — настройка проекта. Основа:

| Факт | Источник (правится здесь) | Производное (генерируется или ссылается) |
|---|---|---|
| Значение параметра | таблица параметров спеки компонента-владельца | Deploy («Конфигурация»), карточки блоков, архитектура — ссылкой или подстановкой |
| Интерфейс: стороны, назначение, модели | данные интерфейсов (YAML, [по единице](data.md#yaml)) + параметры и интерфейсы спек-участников | карточки «Интеграции», схема C1 |
| Модель данных (поля, типы) | единица модели (YAML) | контракты на вкладке «Интеграции», примеры API сверяются с полями |
| Таблицы БД | схема БД (импорт из работающей системы) / единица таблицы (YAML) | ER-диаграммы, таблицы полей, политика |
| Параметр, настраиваемый в другом модуле | спека-владелец | строка в спеке-настройщике; значения и границы совпадают, правятся обе строки сразу |
| Ссылка на требование | якорь у заголовка требования | ссылки из задач, трассировки, R&D |
| Задачи | документы задач, Roadmap | списки задач в изменениях спек, индексы |

<a id="cross-spec"></a>

## Изменение, касающееся нескольких спек
- **Частное** (своя конфигурация, свои хранилища, свои интерфейсы, свои отказы): правка — **во все** затронутые спеки, в каждой — своим содержанием. Одинаковый шаблонный текст в нескольких спеках — дефект: частное описано как общее.
- **Связующее** (интерфейс между модулями, общий формат, сквозной процесс): правка — **обязательно во все** спеки-участники. В каждой — своя сторона связи: что модуль отдаёт или принимает, по какому интерфейсу (I-код), что делает при отказе другой стороны. Проверка сверяет обе стороны.
- Реализация может быть общей (библиотека, сервис), но в спеках это собственные требования каждого модуля.

<a id="req-task-trace"></a>

## Двусторонняя трассировка требование ↔ задача
- У каждого требования — постоянный ID `R-<спека>-NN` и строка «Реализует задача»; ID не меняется при переименовании и не переиспользуется.
- У каждой задачи — раздел «Закрывает требования»; в Roadmap и сводной таблице — колонка «Требования».
- Проверка: каждое требование покрыто задачей или решением «бэклог»; связь совпадает с обеих сторон; у открытой задачи есть требование.

<a id="task-intake"></a>

## Приёмка новой задачи
Задачу мог поставить агент без контекста. До попадания в Roadmap её проверяет агент **с контекстом**:

1. **Найти требование**, которое закрывает задача (поиск по ID и смыслу во всех спеках и историях).
2. **Требование есть и описано достаточно** → взаимные ссылки задача ↔ требование.
3. **Требование есть, но размыто** (разночтения: кто, когда, что дальше) → задача закрывается с указанием ID требования; требование уточняется.
4. **Требования нет** → сначала история и требование в спеке, потом задача.
5. Задача без требования в Roadmap не попадает (проверка).

Объединение задач: если виден общий модуль, задачи можно объединить; объединённая перечисляет все закрываемые требования и остаётся в рамках INVEST (до ~5 дней человека), иначе — делить.

<a id="bulk"></a>

## Массовые изменения
Когда исправлений много (проверка ролями, ревью, смена методологии), цикл «по одному документу» тратит слишком много: одни и те же источники, проверки и сборки повторяются десятки раз.

| Шаг | Что делаю | Сколько раз |
|---|---|---|
| 1. Все проверки | проверка ролями, `check`, сборка — полный список замечаний сразу; замечания — в файл компонента ([замечания](review.md#findings)) | один раз до правок |
| 2. Зафиксировать состояние | коммит: решения ролей и список замечаний в репозитории | один раз |
| 3. Партия исправлений | замечания группируются по слою и источнику (решения и требования → данные и интеграции → блоки → Deploy → истории → задачи → R&D); партия — все правки одного источника за один проход | по партии |
| 4. Связанные документы партии | по графу — для всей партии сразу; методологию читаю один раз на партию | по партии |
| 5. Проверка и коммит партии | `check`, сборка, статусы замечаний, коммит | один раз на партию |
| 6. Повторная проверка ролями | только документы, у которых сброшены подтверждения | один раз в конце |

**Исполнение партии — один скрипт, потолок вызовов.** Расход ≈ вызовы × средний контекст: агент, правящий файлы по одному, тратит 50–100 вызовов и 1–16 млн токенов на компонент. Партию делает агент [doc-bulk-editor](../agents/doc-bulk-editor.md) (Sonnet, `maxTurns: 10`): одна команда — список целей, один Write — скрипт-патч, один Bash — запуск и проверки. Бриф: правило правки, команда целей, проверки, потолок вызовов, что пропускать. Замер пилота: 145 правок в 53 файлах за 7 вызовов — 0,32 млн ([расход](token-costs.md#bulk-edit)). Правки, требующие суждения по каждому месту, — отдельной партией после механических.


<a id="links"></a>

## Переименование, перенос и новый документ
Ссылки — не смысл документа, поэтому правило «по одному документу» к ним не относится.

| Случай | Что делаю | Проверка |
|---|---|---|
| Документ переименован или перенесён | **сразу, одним шагом**: файл и все ссылки и упоминания пути во всех документах (`move`); цепочку по графу не запускаю | битых ссылок 0 |
| Изменился якорь раздела | найти ссылки на `<файл>#<якорь>` и заменить в том же шаге | битых якорей 0 |
| Новый документ | **входящая ссылка**: строка «←» на родителя, место в навигации или строка в индексе своего типа; остальные связи — шагами по графу | «сирот» нет |

<a id="rules-change"></a>

## Изменение правил и методологий
Правила — источник для людей **и** для инструментов: выжимки `route` строятся из таблиц правил, сценарии и `AGENTS.md` ссылаются на пути, проверки реализуют правила. Поэтому правка методологии — правка трёх слоёв, в таком порядке:

1. **Сначала инструменты** — иначе агент продолжит работать по старому правилу:
   - разбор таблиц (`route`), список генерируемых файлов, проверки (`check`);
   - новое правило — с проверкой, если её можно автоматизировать;
   - хуки редактора и git;
   - сценарии (`skills/`) и `AGENTS.md` — пути, команды, порядок работы;
   - память агента — указатель, если поменялся способ работы.

   Готово, когда `route <файл этого типа>` показывает новое правило, а `check` чист.
2. **Затем документы этого типа:** привести к новой методологии; если не в этом изменении — записать расхождения ([таблица расхождений](doc-types.md#audit)) и завести задачу.
3. **Таблицы правил:** строка в [типах документов](doc-types.md), при новой вкладке — навигация.

«Справка» содержит только общее; новая страница там — только если она не про данные конкретных компонентов.

<a id="deviations"></a>

## Отклонения
Найдено отклонение (ошибка, расхождение, пропуск) → **сначала причина**: почему правила его допустили → **затем правило** (и, если можно, проверка) → строка в [журнале отклонений](deviations.md) → исправление самого документа. Исправление без правила не считается законченным.

<a id="sync"></a>

## Матрица синхронизации
Изменили слева → проверить справа. Адаптируйте под свои типы документов.

| Изменение | Проверить и при необходимости обновить |
|---|---|
| Новое решение / смена технологии | R&D → решения (D) → архитектура → спека (Purpose) → данные компонента и блоков → схемы спек |
| Новая или изменённая User Story | истории → требования и сценарии → трассировка → задачи → Roadmap |
| Новое требование | ID → трассировка → «Закрывает требования» задачи → Roadmap; «Как работает»; при разрыве — задача или «не в MVP» |
| Новая задача | приёмка задачи → Roadmap (строка и итоги) → сводная таблица → индексы |
| Новый параметр конфигурации | таблица параметров спеки → сценарий конфигурации → Deploy («Конфигурация» генерируется) → карточки блоков |
| Новый блок | файл единицы блока (`yaml-fmt` — в `_order.yaml`) → схема C3 и карточка блока (генерируются) |
| Новая или изменённая модель, интеграция, имя | файл данных → примеры API → [два читателя](dual-read.md) |
| Новый интерфейс, хранилище или таблица | параметры и интерфейсы **всех** спек-участников → файл данных → каталог API → «Как работает» |
| Новый компонент | README → архитектура → данные компонентов → интеграции → «Как работает» → спека → Deploy → R&D |
| Новая технология / версия | R&D → технологии → решения → спека → задачи |
| Новая зависимость модуля | FMEA → требование «Поведение при отказах» (сценарий) |
| Решение меняет владельца данных или направление вызова | хранилища и интерфейсы **всех** спек-участников → требования → «Как работает» |
| R&D меняет решение (последствия Э10) | решения → требования спек-участников → параметры и интерфейсы → «Как работает» → API → Deploy → задачи → технологии; у каждой строки — статус |
| Новый открытый вопрос | вопросы спеки → «Что проработать» задачи; 📌 — владельцу |
| Решение по вопросу 📌 | решения (D) → спека → вопросы (удалить) → задачи |
| Ревью | у замечания — ID и спека → ❓ / 📌 в вопросы спеки → «Что проработать» задач |
| Новый тип документа | [типы документов](doc-types.md) → граф → навигация |
| Изменение правила или методологии | [порядок выше](#rules-change): инструменты → документы типа → таблицы правил |

<a id="archive"></a>

## Архивация изменений
Если спеки ведутся изменениями (формат с дельтами, например OpenSpec): изменение архивируется только после **реализации и приёмки** всех его задач — тогда его спеки становятся действующим описанием системы. Раньше нельзя: архивация объявила бы действующим то, чего нет в коде. Вместе со спекой переносятся её соседние файлы (параметры, трассировка, подтверждения, вопросы), ссылки переключаются на новый путь, затем проверки.
