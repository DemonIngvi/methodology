# Методология Deploy

← [Правила](README.md) · [роли](roles.md) · [шаблон](../templates/deploy.md)

Как вести вкладку «Deploy» компонента (`deploy/<компонент>.md`): образы, запуск, переменные и секреты, сборка и поставка, проверка после развёртывания.

## Назначение и читатель

Отвечает на вопрос **«как это собрать, откуда взять и как безопасно запустить»**. Читатель — инженер сборки и поставки, DevOps-инженер, безопасность. Порядок работы компонента сюда не входит — он в [«Как работает»](architecture.md#how). Пишет роль «Инженер сборки и поставки».

Правило нужно потому, что спеки описывают поведение и параметры, но не технику поставки: как собирается образ, на какой базе, откуда кластер его скачивает, под каким пользователем он работает.

## Основа

| Практика | Что берём |
|---|---|
| [12-Factor App](https://12factor.net) | конфигурация — в переменных среды; сборка, выпуск и запуск разделены |
| [Kubernetes Pod Security Standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/) (restricted) | non-root, без лишних capabilities, `no-new-privileges`, seccomp RuntimeDefault, read-only rootfs |
| [SLSA](https://slsa.dev), SBOM | воспроизводимая сборка, закреплённые базы, SBOM и проверка уязвимостей до публикации |

## Из чего состоит

Заголовок — `# Deploy: <компонент>`; шапка — ссылки на компонент и эту методологию.

| Раздел | Что указать |
|---|---|
| Образы | имя; база (закреплённая по digest); что внутри (версии ключевых библиотек); как собирается (Dockerfile, стадии, lock-файл); откуда берём (свой реестр или внешний с копией у себя); теги (semver + sha, без `latest`); пользователь (non-root); порты; проверка готовности |
| Запуск | namespace, реплики, команда старта (миграции до старта), ограничения безопасности, сеть, тома |
| Переменные и секреты | каждая переменная: зачем, откуда; секреты — только из хранилища секретов; значение — ссылкой на параметры спеки |
| Сборка и поставка | шаги CI по одному разу: сборка, тесты, SBOM, проверка уязвимостей, публикация |
| Проверка после развёртывания | короткий список действий, подтверждающих, что компонент работает |
| Обновление и откат (если есть данные или миграции) | порядок обновления, точка восстановления, откат образа и откат после миграции, восстановление **всех** хранилищ компонента, ключи, без которых данные не прочитать |
| Конфигурация (генерируется) | все настраиваемые параметры компонента — из таблиц параметров его спек: имя **как в конфиге**, что задаёт, уровень, где задаётся, по умолчанию, мин–макс. Русское название вместо имени — не параметр: сначала имя в спеке. Руками не пишется |
| Пример конфигурации (если есть файлы настроек) | как настройки лежат в развёртывании; значения — из спеки, новых здесь нет |

**Компонент — чужой форк или внешний продукт:** «Образы», «Запуск», «Переменные», «Сборка» — **по его коду** (Dockerfile, чарт, пример переменных, CI) с датой сверки; расхождение «как есть» и «как нужно» — обе колонки и задача на доработку. Пример конфигурации переопределяет умолчания чарта, которые не подходят системе (образ, встроенные БД и хранилища в пользу общих, секреты из хранилища, тома для записи при read-only rootfs). Если upstream задаёт базу тегом — указать тег и где закрепляется digest.

**Встроенный компонент:** у хоста — строка «Встроенные компоненты» со ссылками; у встроенного — «в составе образа <хост>», без второго описания образа.

Каждая технология из Deploy — строка в списке технологий (лицензия, источник).

## Как вести

| Триггер | Что сделать |
|---|---|
| Новый компонент или сервис | страница Deploy до первой задачи реализации |
| Новая технология, база образа, реестр | обновить «Образы» и технологии |
| Изменение развёртывания (реплики, ресурсы, порты, переменные, секреты) | обновить «Запуск» и «Переменные и секреты» |
| Приёмка задачи, затрагивающей сборку или развёртывание (Definition of Ready) | Deploy описывает нужное; иначе дополнить до начала работ |
| Перед выпуском (Definition of Done) | сверить образы, теги и проверки готовности с фактом |
| Обновление зависимости | версия и digest базы, повторная проверка уязвимостей |

## Чек-лист качества

- [ ] Заголовок «Deploy: <компонент>», шапка ведёт на компонент и методологию.
- [ ] База образа закреплена по digest (или указано, где закрепляется).
- [ ] Тег — semver + sha, `latest` нет.
- [ ] В «Запуске» есть ограничения безопасности.
- [ ] Значения параметров — ссылками на спеку; «Конфигурация» не правится руками.
- [ ] Каждый шаг сборки и поставки — один раз.

## Проверки

У каждого компонента есть страница Deploy с обязательными разделами; в Deploy нет «Как работает»; «Конфигурация» собирается из спек; имя параметра — латиница, цифры, `.`, `_`; при данных или миграциях есть «Обновление и откат» (lint).

Проверяет lint (`lint`): у компонента с данными (поле «Данные» его блоков) «Обновление и откат» говорит о миграциях; проектное (например, параметры в values → раздел «Пример конфигурации») — плагином проекта.
