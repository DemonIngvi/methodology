# Методология данных и интеграций

← [Правила](README.md) · [API](api.md) · [два читателя](dual-read.md)

Как вести модель данных, контракты обмена, интеграции между компонентами, таблицы БД и имена: вкладки «Интеграции» (схема C1, карточки, контракты) и «Данные» (хранилища, ER, политика таблиц).

## Назначение и читатель

Отвечает на вопросы **«кто с кем связан, что передаётся, что хранится и почему так названо»**. Читатель — разработчик, который реализует интерфейс, и проверяющий, который сверяет спеки. По одной странице он должен понять поле: что оно значит, откуда взято (код внешней системы, внешний протокол или наше решение) и почему так называется.

Расход: см. [чтение единицы](token-costs.md#unit-read), [перенос данных в YAML](token-costs.md#yaml-migration) на странице «Расход токенов».

## Из чего состоит

| Что | Где задаётся (в файле данных) | Что генерируется |
|---|---|---|
| Интерфейс (I-код) | кто вызывает → кого, через что, что передаётся, модели; отметка «данные в ответе»; общая инфраструктура интерфейса; строка в параметрах и интерфейсах спек-участников (протокол, доступ, таймауты, повторы) | вкладка «Интеграции» (схема C1, карточки), «получает / отдаёт» |
| Модель (контракт JSON) | поля; источник поля (есть в работающей системе ✅ / внешний протокол 📘 / наше решение 🧩); сноска «почему так»; планируемые доработки с D / R; пример — в каталоге API | «Контракты данных» на вкладке «Интеграции» |
| База данных и схема | кластер → база → схема; у схемы — владелец (компонент), роль БД сервиса, кто мигрирует, S-код; доступ к чужим таблицам — только явным разрешением | «Данные» Инфраструктуры и компонента |
| Таблица БД | колонки, ключи, FK; политика: индексы, срок, очистка, миграции; таблицы существующей системы — импортом схемы | ER-диаграммы, таблицы полей, политика |
| Имена | правило имён в файле данных | раздел «Правило имён» |

Где задаётся — поля единиц данных; раскладка файлов — [ниже](#yaml).

## Источник данных — YAML по единице
Данные документации (компоненты, блоки, модели, таблицы, эндпоинты, интерфейсы, истории, процессы) лежат в папке данных (например, `data/`) — **один файл на единицу** (1–3 КБ): агент читает и правит только её, а не монолитный файл данных на десятки тысяч токенов. Страницы и схемы из этих файлов **генерируются**.

| Единица | Файл (пример раскладки) |
|---|---|
| Компонент | `data/components/<slug>.yaml`; порядок — `_order.yaml` папки |
| Блок компонента | `data/blocks/<компонент>/<slug>.yaml`; имя файла = адрес страницы блока |
| Модель (контракт JSON) | `data/models/<Имя>.yaml` |
| Таблица БД | `data/tables/<имя>.yaml` |
| Эндпоинты страницы API | `data/endpoints/<страница>.yaml` |
| Интерфейсы, базы, общее | `data/integrations.yaml`, `data/databases.yaml` (запись на I-код, базу) |
| История, процесс | `data/stories/<компонент>/<ID истории>.yaml`, `data/processes/<компонент>.yaml` |

- **Правится только YAML.** Поля, типы, обязательность, допустимые значения и ссылки на каталоги ID (требования, задачи, истории, таблицы, I-коды) — схема вида единицы в конфиге инструмента (`[[data.kinds]]`, [doctool](../tools/README.md#data)); проверка — `yaml-check` (входит в `check`).
- **Читать единицу — `unit <ID>`**: YAML без пустых полей + строка «связано: …» (на что ссылается и кто ссылается на неё) — вместо страницы и целого файла данных.
- **Формат — `yaml-fmt [путь]`**: порядок ключей по схеме, единый стиль; новая единица вносится в `_order.yaml` папки. Единица не в `_order.yaml` — замечание `yaml-check`.
- **Сгенерированные страницы руками не правятся** (`pre <файл>` называет источник); сборка — **один раз в конце пути изменений**, не после каждой единицы ([порядок](change-process.md#yaml-path)).
- YAML читается библиотекой PyYAML; без неё `yaml-check`, `yaml-fmt`, `unit` завершаются ошибкой «нужен PyYAML», а `check` пропускает проверку данных с предупреждением. Вручную: открыть файл единицы, сверить поля со схемой вида в конфиге, ссылки — поиском ID.

<a id="yaml-units"></a>

### Схема единиц

Схема строгая: ошибка в значении ловится при `yaml-check`, а не на ревью.

- **Строка таблицы — словарь с именованными полями**, а не позиционный список `[a, b, c]`: поле видно по имени, пропуск необязательного не сдвигает остальные; строка пишется в одну строку (`- {dir: ←, with: Poller, what: …}`). Обязательные поля и «хотя бы одно из» (`one_of`) задаёт схема вида.
- **ID — в своих полях**, не внутри текста (`via`, `reqs`, `decisions`, `table`, `model`, `endpoint`); текст остаётся текстом, если ID не извлекается без потерь.
- **ID из полей не теряются при записи.** Запись единицы (`yaml-fmt`, `yaml-migrate`, перенос) не должна молча терять ID из полей-списков (`[data] guard_id_fields`, например `via`, `reqs`, `decisions`): ID, который пропал из поля, но по-прежнему стоит в тексте строки, возвращается в поле; иначе запись отклоняется с перечнем ID, файл не меняется. Намеренное удаление — явный параметр записи `drop_ids`. Причина: сборка поля из текста не повторяет ID, уже стоящий в тексте, и при записи поле тихо опустело бы.
- **Поле-ссылка принимает только значение из каталога** (`ref`; несколько каталогов — списком; значения вне каталога по шаблону — `also`). Каталоги не ведутся руками: вид единиц (его ID), требования, задачи, `[ids.*]` — и каталоги, которые проект объявляет в конфиге `[[data.catalogs]]`: откуда собирать ID — виды единиц (`kinds`), поля единиц (`fields`), регулярка по файлам (`files`), перечисление (`values`). Каталог псевдонимов участников (подпись → участник каталога) — единица-словарь, ключи которой берутся в каталог через `keys`: так подписи в строках взаимодействий допустимы, а значения словаря проверяются на принадлежность каталогу участников. Значение не из каталога — замечание с **ближайшими вариантами** («может быть: …»); то же для недопустимого значения `choices` и поля не из схемы.
- **Параметр**: имя — из таблиц параметров спек компонента (`[data.params]`: файлы и названия колонок), значение (`param_value`) — по типу из колонок «по умолчанию / мин / макс»: число с границами и единицей, длительность, перечисление. Описанное словами не формализуется — пояснение идёт в отдельное поле.
- **«нет: <почему>»** — допустимое значение списковых полей карточки (`none_ok`: `data`, `params` и им подобных) у блока без таблиц или настроек; причина обязательна, поле считается заполненным.
- **JSON Schema для редактора**: `yaml-schema` пишет схему каждого вида (`enum` из каталогов) и сопоставление файлов в `.vscode/settings.json` (`yaml.schemas`; чужие настройки сохраняются). Редактор подсказывает поля и значения до `yaml-check`; `check` сообщает, если схема устарела (изменился конфиг или каталог).
- **Перевод**: `yaml-migrate` — механизм, правила проектные: `positional` в схеме (позиционный вид → именованные поля) и правила плагина (например, вынести ID из текста в поле). Идемпотентен; что осталось текстом — списком для ручного разбора. Параметры инструмента — [doctool](../tools/README.md#data).

<a id="naming"></a>

## Правило имён
Правило задаёт проект; основа:

- JSON собственных контрактов — в одном стиле (например, camelCase, как в API основной системы);
- единица измерения — суффиксом (`readyMs`, `ttlSec`);
- внешние протоколы — в их стиле;
- колонки БД и параметры конфигурации — snake_case;
- **один объект — одно имя** во всех моделях.

## Как вести

| Когда | Шаги |
|---|---|
| Новый интерфейс | 1) стрелка — кто вызывает; данные в ответе — отметить; 2) тип данных; 3) строка с I-кодом в спеках **всех** участников; 4) эндпоинты в каталоге API; 5) два читателя |
| Новая модель или поле | 0) модель указана в интерфейсе, по которому передаётся; 1) поля с описанием каждого; 2) источник: поле есть в работающей системе — ✅, доработка — с D / R, внешний протокол — 📘, наше — 🧩; 3) сноска «почему так» — со ссылкой на **существующие** D или R; 4) пример в каталоге API |
| Поле контракта хранится в БД | колонка в таблице-источнике; доработка чужой таблицы — строкой в списке колонок с решением, а не заметкой «+ колонка» |
| Новая база, схема или роль | 1) владелец, роль, миграции, S-код; 2) Deploy сервиса — строка подключения с базой и ролью; 3) решение о размещении — R&D и D, если меняется граница |
| Новая таблица | колонки, ключи, FK; политика: индекс на каждом FK, срок, очистка, кто мигрирует |
| Компонент пользуется общей инфраструктурой интерфейса | на C1 — пунктир к инфраструктуре с I-кодом; карточка с пометкой «общая инфраструктура» |
| Интерфейс внутри компонента | на C1 не рисуется (C1 — стыки с соседями); карточка с пометкой «внутри компонента» |
| Таблица существующей системы, в которую пишет наш компонент | политика с индексами «как есть»; срок и очистка — по коду системы; срок не задан — так и написать и вопрос в спеке |
| На ER нужна таблица другого домена | одним ключом (заглушка), с пояснением |
| Изменилась схема или API существующей системы | повторный импорт схемы и спецификации API, затем проверки |
| Нашли непонятное | вопрос в спеке, а не догадка в описании |

## Чек-лист качества

- [ ] У каждого поля — описание; у модели — источник и «почему так».
- [ ] Ссылки на D и R существуют (проверено поиском); параметров, которых нет в спеках, нет.
- [ ] Поля существующей системы совпадают с её спецификацией API; добавленные — с решением.
- [ ] Стрелка интерфейса — кто вызывает; данные в ответе отмечены.
- [ ] Каждая таблица лежит в описанной схеме с владельцем и ролью; Deploy владельца называет базу и роль.
- [ ] Имена — по правилу; один объект — одно имя.
- [ ] Двое читателей объяснили модели одинаково по смыслу.

## Проверки

`yaml-check` — единицы данных по схеме вида: обязательные поля, типы, допустимые значения, ссылки на существующие ID, `_order.yaml`. I-коды = интерфейсы спек в обе стороны; модели существующей системы = её спецификация API; примеры API = поля моделей (точные имена); FK покрыты индексами; у таблиц есть политика; схема каждой таблицы описана; импорт схемы соответствует версии системы.

## Типичные ошибки

| Ошибка | Как правильно |
|---|---|
| Модель по замыслу, а не по коду существующей системы | по коду и спецификации API |
| Поля в трёх местах (поток, API, модель) разошлись | одна модель, остальное — ссылки и сверка |
| Связь описана только у одной стороны | во всех спеках-участниках |
| Один объект назван несколькими способами | одно имя по правилу |
