# Методология данных и интеграций

← [Правила](README.md) · [API](api.md) · [два читателя](dual-read.md)

Как вести модель данных, контракты обмена, интеграции между компонентами, таблицы БД и имена: вкладки «Интеграции» (схема C1, карточки, контракты) и «Данные» (хранилища, ER, политика таблиц).

## Назначение и читатель

Отвечает на вопросы **«кто с кем связан, что передаётся, что хранится и почему так названо»**. Читатель — разработчик, который реализует интерфейс, и проверяющий, который сверяет спеки. По одной странице он должен понять поле: что оно значит, откуда взято (код внешней системы, внешний протокол или наше решение) и почему так называется.

## Основа

| Практика | Что берём |
|---|---|
| Контракт данных, JSON Schema | у модели — поля, типы, обязательность, описание, владелец |
| OpenAPI 3 | структура существующих API — из спецификации работающей системы, не по памяти |
| ER-модель | таблицы, ключи, связи; индекс на каждом внешнем ключе; срок хранения и очистка |
| [Один источник](change-process.md#single-source) | всё описано в одном файле данных, страницы генерируются |
| [Два читателя](dual-read.md) | понятность имён и описаний проверяется независимыми читателями |

## Из чего состоит

| Что | Где задаётся (в файле данных) | Что генерируется |
|---|---|---|
| Интерфейс (I-код) | кто вызывает → кого, через что, что передаётся, модели; отметка «данные в ответе»; общая инфраструктура интерфейса; строка в параметрах и интерфейсах спек-участников (протокол, доступ, таймауты, повторы) | вкладка «Интеграции» (схема C1, карточки), «получает / отдаёт» |
| Модель (контракт JSON) | поля; источник поля (есть в работающей системе ✅ / внешний протокол 📘 / наше решение 🧩); сноска «почему так»; планируемые доработки с D / R; пример — в каталоге API | «Контракты данных» на вкладке «Интеграции» |
| База данных и схема | кластер → база → схема; у схемы — владелец (компонент), роль БД сервиса, кто мигрирует, S-код; доступ к чужим таблицам — только явным разрешением | «Данные» Инфраструктуры и компонента |
| Таблица БД | колонки, ключи, FK; политика: индексы, срок, очистка, миграции; таблицы существующей системы — импортом схемы | ER-диаграммы, таблицы полей, политика |
| Имена | правило имён в файле данных | раздел «Правило имён» |

## Правило имён
Правило задаёт проект; основа:

- JSON собственных контрактов — в одном стиле (например, camelCase, как в API основной системы);
- единица измерения — суффиксом (`readyMs`, `ttlSec`);
- внешние протоколы — в их стиле;
- колонки БД и параметры конфигурации — snake_case;
- **один объект — одно имя** во всех моделях.

## Как вести

| Когда | Шаги |
|---|---|
| Новый интерфейс | 1) стрелка — кто вызывает; данные в ответе — отметить; 2) тип данных; 3) строка с I-кодом в спеках **всех** участников; 4) эндпоинты в каталоге API; 5) два читателя |
| Новая модель или поле | 0) модель указана в интерфейсе, по которому передаётся; 1) поля с описанием каждого; 2) источник: поле есть в работающей системе — ✅, доработка — с D / R, внешний протокол — 📘, наше — 🧩; 3) сноска «почему так» — со ссылкой на **существующие** D или R; 4) пример в каталоге API |
| Поле контракта хранится в БД | колонка в таблице-источнике; доработка чужой таблицы — строкой в списке колонок с решением, а не заметкой «+ колонка» |
| Новая база, схема или роль | 1) владелец, роль, миграции, S-код; 2) Deploy сервиса — строка подключения с базой и ролью; 3) решение о размещении — R&D и D, если меняется граница |
| Новая таблица | колонки, ключи, FK; политика: индекс на каждом FK, срок, очистка, кто мигрирует |
| Компонент пользуется общей инфраструктурой интерфейса | на C1 — пунктир к инфраструктуре с I-кодом; карточка с пометкой «общая инфраструктура» |
| Интерфейс внутри компонента | на C1 не рисуется (C1 — стыки с соседями); карточка с пометкой «внутри компонента» |
| Таблица существующей системы, в которую пишет наш компонент | политика с индексами «как есть»; срок и очистка — по коду системы; срок не задан — так и написать и вопрос в спеке |
| На ER нужна таблица другого домена | одним ключом (заглушка), с пояснением |
| Изменилась схема или API существующей системы | повторный импорт схемы и спецификации API, затем проверки |
| Нашли непонятное | вопрос в спеке, а не догадка в описании |

## Чек-лист качества

- [ ] У каждого поля — описание; у модели — источник и «почему так».
- [ ] Ссылки на D и R существуют (проверено поиском); параметров, которых нет в спеках, нет.
- [ ] Поля существующей системы совпадают с её спецификацией API; добавленные — с решением.
- [ ] Стрелка интерфейса — кто вызывает; данные в ответе отмечены.
- [ ] Каждая таблица лежит в описанной схеме с владельцем и ролью; Deploy владельца называет базу и роль.
- [ ] Имена — по правилу; один объект — одно имя.
- [ ] Двое читателей объяснили модели одинаково по смыслу.

## Проверки

I-коды = интерфейсы спек в обе стороны; модели существующей системы = её спецификация API; примеры API = поля моделей (точные имена); FK покрыты индексами; у таблиц есть политика; схема каждой таблицы описана; импорт схемы соответствует версии системы.

## Типичные ошибки

| Ошибка | Как правильно |
|---|---|
| Модель по замыслу, а не по коду существующей системы | по коду и спецификации API |
| Поля в трёх местах (поток, API, модель) разошлись | одна модель, остальное — ссылки и сверка |
| Связь описана только у одной стороны | во всех спеках-участниках |
| Один объект назван несколькими способами | одно имя по правилу |
