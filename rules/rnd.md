# Методология R&D (v3.1, сжато)

← [Правила](README.md) · [решения](decisions.md) · [шаблон](../templates/rnd.md) · [сценарий](../skills/doc-rnd.md)

Исследование идёт по цепочке **потребность → ключевые функции → ценность → перенос → встраивание в схему → спор ролей → выбор → последствия**. Каждый этап начинается с выхода предыдущего и закрывается воротами. Критерии выбора получаются в конце цепочки, а не задаются заранее. Выводы доказываются фактами; цифры — только для сверки, в приложении.

Два вида R&D: **выбор решения** (технология, архитектурный подход, методика) и **потоки пользователей** (для историй, [ниже](#us-rnd)).

<a id="gates"></a>

## Цепочка этапов
| Этап | Что делаем | Выход | Ворота: идём дальше, если… | Иначе |
|---|---|---|---|---|
| **Э1 Вопрос** | ситуация, осложнение, вопрос (SCQA): вопрос — выбор между вариантами; кто решает; что не решаем | «Вопрос» | вопрос — выбор; есть владелец; есть связь с историей, требованием или решением | это задача, а не R&D |
| **Э2 Потребности** | что должно получаться (JTBD), а не функции; у потребности — источник и «что ломается без неё» | таблица потребностей | у каждой есть источник; нет «на всякий случай» | → Э1 |
| **Э3 Опорное решение** | ключевые функции того, что есть или предполагается: что делает, какую потребность закрывает, факт | таблица функций | каждая функция связана с потребностью; наличие подтверждено уровнем Б+ | → Э2 |
| **Э4 Альтернативы** | широкий поиск с датой; всегда «как сейчас / ничего не делать» и «сделать самим»; функции по тем же потребностям | длинный список | ≥ 5 кандидатов из ≥ 3 видов источников; по каждой потребности видно, как её закрывает каждый | → Э4: расширить поиск |
| **Э5 Ценность** | для функции: какую потребность закрывает, **почему ценна** (механизм), доказательство (А–Г), класс (Kano) | таблица ценности | у берущихся функций ценность подтверждена уровнем Б+; Г → прототип или «не берём» | → Э4 |
| **Э6 Перенос и критерии** | по каждой функции: **брать / адаптировать / заменить / не брать** с причиной; базовые → MUST, линейные → критерии, привлекательные → доп. критерии | таблица переноса, критерии с цепочкой | у каждой функции решение; у критерия цепочка «потребность → функция → ценность → класс» | → Э5 |
| **Э7 Отсев и встраивание** | отсев по MUST до сравнения; для прошедших — **как встаёт в общую схему** ([ниже](#integration)); схема C1 для лидеров | таблица отсева, встраивания, схема | у прошедшего есть строка встраивания по всем затронутым интерфейсам; изменения у соседей названы | → Э4 |
| **Э8 Спор ролей** | роли, чьи требования и интерфейсы затронуты, спорят ([ниже](#debate)) | позиции, разрешение споров | у каждого спора — разрешение или 📌 владельцу | → Э5–Э7 |
| **Э9 Выбор** | сравнение словами: «закрывает / с доработкой (что и сколько) / не закрывает» с фактом; риски лидера; вывод аргументом (Тулмин); условия пересмотра | «Выбор», первая страница | вывод следует из сравнения; у вывода есть условие, при котором он неверен | → Э5 или прототип |
| **Э10 Последствия** | что меняет выбор во **всей цепочке** документов ([ниже](#consequences)) | таблица последствий | у изменения — целевой документ и статус; внесённые прошли процесс изменения | → Э9 |

**Финальные проверки** (четыре качества отчёта, GAO TRA): **достоверность** (у факта источник и дата, уровни доказательства), **объективность** (рассмотрены «ничего не делать» и «сделать самим», выслушаны противоположные роли, у вывода есть опровержение), **воспроизводимость** (можно повторить путь), **полезность** (первая страница отвечает и говорит, что делать).

**Сокращённый путь** — для малого вопроса: Э3 и Э4 в одну таблицу, в Э8 — 2–3 роли. Встраивание (Э7) и последствия (Э10) не сокращаются.

<a id="integration"></a>

## Встраивание в общую схему
Решение оценивается **на своём месте в архитектуре**: кандидат с лучшими функциями может требовать перестройки соседей — это цена выбора.

| Что смотрим | Вопрос |
|---|---|
| Интерфейсы | какие I-коды занимает или меняет; совпадают ли протокол и формат |
| Направление вызовов | кто кого вызывает; не ломаются ли принятая модель взаимодействия и границы модулей |
| Данные и владельцы | чьи хранилища читает и пишет; не появляется ли второй владелец данных |
| Развёртывание | свой сервис, часть существующей системы, внешний образ; новые зависимости эксплуатации |
| Изменения у соседей | что придётся поменять в других компонентах |
| Безопасность на стыках | новые пути данных и секретов |

**Готовность интеграции** (упрощённая шкала IRL): **И0** стык не описан · **И1** описан в документации кандидата · **И2** протокол и модель совпадают с нашими или расхождение описано · **И3** проверен прототипом · **И4** работает у нас.

<a id="debate"></a>

## Спор ролей
1. **Состав** — роли, чьи требования, истории, интерфейсы или эксплуатация затронуты (обычно 4–6). Агент в роли отмечается 🤖.
2. **Позиции** — за какой вариант; главный довод со ссылкой на факт; главное опасение; при каком условии согласится.
3. **Тезис и антитезис** — назначенный оппонент защищает лучшую альтернативу, «адвокат дьявола» ищет, где лидер провалится.
4. **Разрешение** — условие, задача, требование, смена выбора или 📌 владельцу.
5. **Возврат** — спор вскрыл неучтённую функцию или стык → Э5–Э7.

<a id="consequences"></a>

## Последствия во всей цепочке
| Изменение | Документ | Статус |
|---|---|---|
| что меняется | решение (D), спека (R-…), параметры и интерфейсы **всех спек-участников**, файл данных, «Как работает», API, Deploy, задача, технологии | ✅ внесено · 📌 предложено (ссылка на задачу или вопрос) · — не требуется (почему) |

- **Подтверждение без изменений** — тоже результат: «решение не меняется», затронутые документы со статусом «не требуется».
- **Выбор меняет решение, стек или описание** — изменение по [процессу изменения](change-process.md); слишком большое — задача.
- Смена версии или технологии обновляет список технологий и Deploy.

<a id="kano"></a>

## Классы функций (Kano)
| Класс | Признак | В Э6 |
|---|---|---|
| Базовая | без неё работа не выполняется; есть у всех аналогов | **MUST**: отсев до сравнения |
| Линейная | чем лучше, тем лучше закрыта потребность | критерий сравнения |
| Привлекательная | улучшает, но отсутствие не мешает | доп. критерий при равенстве |
| Безразличная | не закрывает нашу потребность | не берём, причина |
| Обратная | мешает работе или противоречит решению | не берём; у выбранного — отключить |

Классы смещаются со временем — факты о функциях аналогов проверяются **на дату**.

<a id="evidence"></a>

## Уровни доказательства
**А** — проверено нами (код, прототип, замер) · **Б** — первичный источник (документация, код, changelog, стандарт) · **В** — опыт практиков (статьи, issue) · **Г** — заявление без деталей (маркетинг, «скоро будет»).

Наличие функции — уровень Б+. Ценность — наша история или требование плюс одно из: функция у ≥ 2 аналогов; опыт практиков (В); наш прототип (А).

<a id="argument"></a>

## Аргумент вывода (Тулмин)
**Утверждение** (что решили) · **Основания** (факты) · **Связка** (почему факты ведут к выводу) · **Оговорка** (насколько сильно) · **Опровержение** (когда вывод неверен).

<a id="layout"></a>

## Подача результата
«Ответ первым» (пирамида Минто). **Первая страница — презентация для заказчика на 3 минуты**, без таблиц баллов:

1. **Вопрос и ответ** одной фразой, статус Tech Radar, ссылка на решение.
2. **Микропрезентация** — до 6 слайдов, каждый — один вопрос заказчика и строка-вывод; пропорции берутся из таблиц этапов: покрытие потребностей (Э9), **объём доработки** (обязателен; из оценок задач или порядковой шкалы), встраивание (Э7), позиции ролей (Э8), что меняется (Э10). Без сумм баллов.
3. **Почему** — 3 карточки: вывод, ключевой факт, ссылка на этап.
4. **Берём / адаптируем / не берём.**
5. **Отсеяны** (одна причина у каждого); **риски и пересмотр**.
6. **Путь исследования** — цепочка этапов.

Дальше — этапы Э1–Э10, каждый со строкой «**Вывод этапа**» и воротами. **Приложение** (сворачиваемое): карточки кандидатов, числовая сверка («сверка, не основание»), сырые данные. **Источники** — с датой и уровнем доказательства.

Текст: вывод — связной фразой с причиной; у факта о продукте — ссылка; «нет функции» — только после проверки изданий (функция может быть в платном).

<a id="search"></a>

## Где искать альтернативы
GitHub (темы, звёзды, лицензия, последний коммит за 12 месяцев, архивирован ли); списки «awesome-…», CNCF Landscape; AlternativeTo, Product Hunt; документация и changelog лидеров рынка **на дату**; статьи «<технология> alternatives <год>»; то, что уже есть в собственном стеке.

**Карточка кандидата** (приложение): ключевые функции по потребностям; расширяемость и лицензия; издания и цена; размещение и ресурсы; здоровье проекта (контрибьюторы, релизы, OpenSSF Scorecard); безопасность; совместимость с нашим стеком.

## Технологии ИИ-агентов: проверка прототипом

Ценность агентной технологии подтверждается прототипом (уровень А); без прототипа статус — не выше **Trial**. Измерения: **AG1** выполнение задачи · **AG2** выбор инструментов и аргументы · **AG3** восстановление после ошибок · **AG4** связность плана · **AG5** эффективность (токены, задержка, стоимость) · **AG6** наблюдаемость и evals. Прототип: 5–10 эталонных задач на mock-LLM и реальной модели.

## Антипаттерны

| Антипаттерн | Как правильно |
|---|---|
| Критерии и веса заданы до разбора функций | критерий — результат Э6 с цепочкой |
| Итог — сумма баллов | вывод аргументом; баллы — сверка в приложении |
| Сравниваются продукты целиком | решение по каждой функции, в том числе у отсеянных |
| Обязательное свойство как взвешенный критерий | базовая функция → MUST, отсев до сравнения |
| Ценность «очевидна» | механизм ценности и доказательство |
| Первая страница — таблица | вопрос → ответ → 3 основания → перенос → риски |
| Решение оценено отдельно от схемы | встраивание по интерфейсам и хранилищам (Э7) |
| Выбор с одной позиции | спор ролей с оппонентом и «адвокатом дьявола» (Э8) |
| R&D без последствий | таблица последствий со статусами (Э10) |
| Факты по памяти | ссылка и дата; проверка изданий |
| Общая таблица критериев для всех R&D | критерии каждого R&D — из его потребностей |

<a id="us-rnd"></a>

## R&D пользовательских потоков
Тот же принцип, единица анализа — поток пользователя: 1) работы (JTBD) по акторам — Э2; 2) 3–5 аналогов и их потоки — Э3–Э4; 3) матрица «поток × аналог × у нас» → истории или «не делаем» с причиной — Э5–Э6; 4) отыгрыш персон и [фильтр необходимости](user-stories.md).
