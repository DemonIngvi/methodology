# Методология R&D (v3.2)

← [Правила](README.md) · [решения](decisions.md) · [шаблон](../templates/rnd.md) · [сценарий](../skills/doc-rnd.md)

**Версия 3.2** ([изменения](#changes)). Исследование идёт по цепочке **потребность → ключевые функции → ценность → перенос → встраивание в схему → спор ролей → выбор → последствия**. Каждый этап начинается с выхода предыдущего и закрывается воротами. Критерии выбора получаются в конце цепочки, а не задаются заранее. Выводы доказываются фактами; цифры — только для сверки, в приложении.

Два вида R&D: **выбор решения** (технология, архитектурный подход, методика) и **потоки пользователей** (для историй, [ниже](#us-rnd)).

**Как читать.** Файл не читается целиком. Этап — отдельный раздел с якорем `e1`…`e10`; читать нужный этап и подразделы, на которые он ссылается (карта — в [сценарии](../skills/doc-rnd.md)). Один раздел — от его якоря до следующего: `sed -n '/^<a id="e3">/,/^<a id="e4">/p' rules/rnd.md`.

## Цепочка этапов

Обзор; подробности — в разделе этапа (ссылка в первой колонке).

| Этап | Выход | Ворота: идём дальше, если… |
|---|---|---|
| [Э1 Вопрос](#e1) | раздел «Вопрос» | вопрос — выбор; есть владелец и связь |
| [Э2 Потребности](#e2) | таблица потребностей | у каждой потребности источник |
| [Э3 Опорное решение](#e3) | функции опорного решения | функции связаны с потребностями, наличие — Б+ |
| [Э4 Альтернативы](#e4) | длинный список, функции альтернатив | ≥ 5 кандидатов из ≥ 3 видов источников |
| [Э5 Ценность](#e5) | ценность функций | ценность берущихся функций — Б+ |
| [Э6 Перенос и критерии](#e6) | перенос, критерии с цепочкой | у функции — решение, у критерия — цепочка |
| [Э7 Отсев и встраивание](#e7) | отсев, встраивание, схема C1 | встраивание по всем затронутым интерфейсам, соседи названы |
| [Э8 Спор ролей](#e8) | позиции, разрешение споров | каждый спор разрешён или 📌 владельцу |
| [Э9 Выбор](#e9) | раздел «Выбор», первая страница | вывод следует из сравнения, есть опровержение |
| [Э10 Последствия](#e10) | таблица последствий | у изменения — документ и статус |

**Финальные проверки** (четыре качества отчёта, GAO TRA): **достоверность** (у факта источник и дата, уровни доказательства), **объективность** (рассмотрены «ничего не делать» и «сделать самим», функции отсеянных разобраны в Э5–Э6, выслушаны противоположные роли, у вывода есть опровержение), **воспроизводимость** (по документу можно повторить путь: источники поиска, дата, критерии с цепочкой), **полезность** (первая страница отвечает и говорит, что делать).

**Сокращённый путь** — для малого вопроса (библиотека, решение одной функции): Э3 и Э4 в одну таблицу функций, в Э8 — 2–3 роли. Встраивание (Э7) и последствия (Э10) не сокращаются; ворота и первая страница — те же.

## Этапы

В документе R&D каждый этап — раздел `## Эn. …`, заканчивается строкой «**Вывод этапа.**» и воротами `Gn ✅ <чем пройдены>` (или ⚠️ — [статус ворот](#gate-status)).

<a id="e1"></a>

### Э1 Вопрос

- **Вход:** история, требование, решение, замечание; в новом продукте — запрос владельца ([ниже](#greenfield)).
- **Что делаем:** ситуация, осложнение и вопрос (SCQA): вопрос — выбор между вариантами; кто решает; что не решаем.
- **Выход:** раздел «Вопрос».
- **G1:** вопрос сформулирован как выбор; есть владелец; есть связь с историей, требованием или решением (в новом продукте — с запросом владельца с датой).
- **Иначе:** это задача, а не R&D.

<a id="e2"></a>

### Э2 Потребности

- **Вход:** выход Э1, истории, требования, ограничения.
- **Что делаем:** что должно получаться (работа и желаемый исход, JTBD), а не функции; у потребности — источник и «что ломается без неё».
- **Выход:** таблица потребностей.
- **G2:** у каждой потребности есть источник; нет потребностей «на всякий случай».
- **Иначе:** → Э1: вопрос шире или уже, чем потребности.

<a id="e3"></a>

### Э3 Опорное решение

- **Вход:** выход Э2.
- **Что делаем:** разбираем то, что есть или предполагается (текущее решение, продукт-кандидат): его **ключевые функции** — без них работа из Э2 не выполняется; у функции — что делает, какую потребность закрывает, факт. Новый продукт — «как пользователь решает задачу без нас» ([ниже](#greenfield)).
- **Выход:** таблица функций опорного решения.
- **G3:** каждая функция связана с потребностью или помечена «не к нашей потребности»; наличие функции подтверждено уровнем Б и выше ([уровни](#evidence)); в новом продукте — по [правилу нового продукта](#greenfield).
- **Иначе:** → Э2: функции закрывают потребности, которых нет в списке, — дописать или убрать.

<a id="e4"></a>

### Э4 Альтернативы

- **Вход:** выходы Э2, Э3.
- **Что делаем:** сначала список кандидатов и видов источников под G4, затем все поиски одной пачкой ([где искать](#search)), с датой. В список всегда входят «как сейчас / ничего не делать» и «сделать самим». У каждой альтернативы — ключевые функции **по тем же потребностям** и функции, которых нет у опорного решения.
- **Выход:** длинный список, таблица функций альтернатив; остальное о кандидате — в [карточке](#candidate-card) приложения.
- **G4:** ≥ 5 кандидатов из ≥ 3 видов источников; для каждой потребности видно, как её закрывает каждый кандидат, или «📌 не подтверждено».
- **Иначе:** → Э4: расширить поиск.

<a id="e5"></a>

### Э5 Ценность

- **Вход:** функции из Э3 и Э4.
- **Что делаем:** для каждой функции — какую потребность закрывает, **почему ценна** (механизм: что станет лучше и за счёт чего), доказательство ([уровни А–Г](#evidence)), класс ([Kano](#kano)). Агентные технологии — прототип по [AG1–AG6](#ag).
- **Выход:** таблица ценности функций.
- **G5:** у каждой функции, которую предлагаем брать, ценность подтверждена уровнем Б и выше; уровень Г → прототип или «не берём».
- **Иначе:** → Э4: искать подтверждение или прототип (spike).

<a id="e6"></a>

### Э6 Перенос и критерии

- **Вход:** выход Э5.
- **Что делаем:** решение по каждой функции — **брать / адаптировать / заменить другой функцией / не брать**, с причиной; из базовых функций — MUST, из линейных — критерии сравнения, из привлекательных — дополнительные критерии ([Kano](#kano)). R&D потоков — здесь матрица «поток × аналог × у нас», отыгрыш персон и фильтр необходимости ([ниже](#us-rnd)).
- **Выход:** таблица переноса, таблица критериев с цепочкой (для потоков — матрица потоков).
- **G6:** у каждой функции (потока) есть решение и причина; у каждого критерия цепочка «потребность → функция → ценность → класс».
- **Иначе:** → Э5.

<a id="e7"></a>

### Э7 Отсев и встраивание

- **Вход:** выход Э6, карта интерфейсов проекта ([данные и интеграции](data.md)).
- **Что делаем:** 1) отсев по MUST до сравнения; 2) для каждого прошедшего — **как встаёт в общую схему** ([встраивание](#integration)): интерфейсы, направление вызовов, чьи хранилища, вид развёртывания, изменения у соседей, готовность И0–И4; схема C1 для лидеров.
- **Выход:** таблица отсева, таблица встраивания, схема C1 (mermaid).
- **G7:** у каждого прошедшего есть строка встраивания по всем затронутым интерфейсам; изменения у соседей названы.
- **Иначе:** → Э4: ни один кандидат не встаёт без перестройки схемы — искать дальше или вынести перестройку в вопрос.

<a id="e8"></a>

### Э8 Спор ролей

- **Вход:** выходы Э6, Э7.
- **Что делаем:** роли, чьи требования, истории или интерфейсы затронуты, спорят о выборе ([спор](#debate)): позиция, главный довод, опасение, условие согласия; лучшую альтернативу защищает оппонент, лидера атакует «адвокат дьявола».
- **Выход:** таблица позиций, таблица разрешения споров.
- **G8:** у каждого спора есть разрешение (условие, задача, требование, смена выбора) или вопрос 📌 владельцу продукта.
- **Иначе:** → Э5–Э7: спор вскрыл неучтённую функцию или стык.

<a id="e9"></a>

### Э9 Выбор

- **Вход:** выходы Э6–Э8.
- **Что делаем:** 1) сравнение по критериям словами: «закрывает / закрывает с доработкой (что и сколько) / не закрывает» с фактом, включая встраивание; 2) риски лидера; 3) вывод аргументом ([Тулмин](#argument)); 4) условия пересмотра.
- **Выход:** раздел «Выбор», первая страница ([подача](#layout)).
- **G9:** вывод следует из сравнения и разрешения споров; у вывода есть условие, при котором он неверен.
- **Иначе:** → Э5 или прототип: факты близки или не подтверждены.

<a id="e10"></a>

### Э10 Последствия

- **Вход:** выход Э9, трассировка.
- **Что делаем:** что меняет выбор во **всей цепочке** документов ([последствия](#consequences)); у каждого изменения — статус «внесено / предложено / не требуется».
- **Выход:** таблица последствий.
- **G10:** у каждого изменения есть целевой документ и статус; внесённые прошли [процесс изменения](change-process.md) и проверки. Новый продукт — допустим полный набор 📌 со следующим шагом ([ниже](#greenfield)).
- **Иначе:** → Э9: последствия дороже выигрыша — пересмотреть выбор.

<a id="greenfield"></a>

## Новый продукт

**Когда:** продукта ещё нет — нет историй, требований, решений и документации проекта (вопрос «делать ли и какой»). Ворота G1, G3, G10 проходятся **по этому правилу** — ✅, а не ⚠️.

| Этап | Обычно | В новом продукте |
|---|---|---|
| Э1 (G1) | связь с историей, требованием, решением | связь — **запрос владельца с датой** (ссылка на сообщение, встречу или цитата) |
| Э2 | источник — наши истории и требования | источник — запрос владельца и внешние факты (рынок, исследования, отзывы); непроверенное у пользователей — 📌 |
| Э3 (G3) | функции существующего решения, наличие — Б+ | **«как пользователь решает задачу без нас»**: обходные пути (звонок, бумага, конкуренты, ничего); наличие — уровень В+ (практики, отзывы, исследования) или ответ владельца; неизвестное о нашей стороне (каналы, системы) — 📌 вопрос владельцу |
| Э10 (G10) | внесено ✅ или предложено 📌 | допустим **полный набор 📌**: у каждой строки — будущий документ и следующий шаг (сценарий, задача); первая строка — README корня проекта с реестром R&D и решений по [шаблону](../templates/project-readme.md) ([структура](structure.md#new-project)) |

Остальные этапы и ворота — без изменений.

<a id="gate-status"></a>

## Статус ворот

| Статус | Значит | Когда |
|---|---|---|
| ✅ пройдено | условие ворот выполнено (в том числе по правилу [нового продукта](#greenfield)) | всегда, когда условие выполнено |
| ⚠️ пройдено условно | условие выполнено не полностью, работа идёт дальше | только если недостающий факт **нельзя получить внутри R&D** (нужен ответ владельца, доступ, пилот), а выбор от него не зависит или зависит явно (условие в Э9) |
| — (не пройдено) | условие не выполнено | возврат по пункту «Иначе» этапа |

⚠️ недопустим, если факт можно найти поиском или чтением, — тогда возврат. В строке ⚠️ обязательно: **что не подтверждено**, **📌 вопрос владельцу** и **следующий шаг**, который снимает условие (задача, пилот, этап). Ворота ⚠️ выносятся в «Риски и пересмотр» первой страницы. Проверка — `rnd-check` ([сценарий](../skills/doc-rnd.md)).

<a id="integration"></a>

## Встраивание в общую схему

Решение оценивается **на своём месте в архитектуре**: кандидат с лучшими функциями может требовать перестройки соседей — это цена выбора.

| Что смотрим | Откуда | Вопрос |
|---|---|---|
| Интерфейсы | карта интерфейсов, интерфейсы спек | какие коды интерфейсов (I-…) занимает или меняет; совпадают ли протокол и формат |
| Направление вызовов | потоки, «Как работает» | кто кого вызывает; не ломаются ли принятая модель взаимодействия и границы модулей |
| Данные и владельцы | хранилища (S-…) в интерфейсах спек | чьи хранилища читает и пишет; не появляется ли второй владелец данных |
| Развёртывание | виды спек, Deploy | свой сервис, часть существующей системы, внешний образ; новые зависимости эксплуатации |
| Изменения у соседей | спеки соседних компонентов | что придётся поменять в других компонентах: требования, интерфейсы, задачи |
| Безопасность на стыках | правила безопасности, секреты | новые пути данных и секретов |

**Готовность интеграции** (упрощённая шкала IRL, Sauser): **И0** стык не описан · **И1** описан в документации кандидата · **И2** протокол и модель совпадают с нашими или расхождение описано · **И3** проверен прототипом у нас · **И4** работает у нас.

Для лидеров — схема C1 места решения ([формат схем](diagrams.md)): соседние компоненты, интерфейсы, направление вызовов; изменённые стыки помечаются `*`.

<a id="debate"></a>

## Спор ролей

Основа — диалектический спор (dialectical inquiry), «адвокат дьявола», участники ATAM со своими сценариями. Роли — из [ролей документации](roles.md) и персон продукта; агент в роли отмечается 🤖.

1. **Состав** — роли, чьи требования, истории, интерфейсы или эксплуатация затронуты (обычно 4–6: архитектор, разработчик, эксплуатация, безопасность, владелец продукта, пользователь, тестировщик).
2. **Позиции** — за какой вариант; главный довод со ссылкой на факт из Э3–Э7; главное опасение; при каком условии согласится.
3. **Тезис и антитезис** — назначенный оппонент защищает лучшую альтернативу, «адвокат дьявола» ищет, где лидер провалится.
4. **Разрешение** — условие, задача, требование, смена выбора или 📌 владельцу, если фактами спор не решается.
5. **Возврат** — спор вскрыл неучтённую функцию или стык → Э5–Э7.

<a id="consequences"></a>

## Последствия во всей цепочке

| Изменение | Документ | Статус |
|---|---|---|
| что меняется | решение (D), спека (R-…), параметры и интерфейсы **всех спек-участников**, файл данных, поток, «Как работает», API, Deploy, задача, технологии | ✅ внесено · 📌 предложено (ссылка на задачу или вопрос, следующий шаг) · — не требуется (почему) |

- **Подтверждение без изменений** — тоже результат: «решение не меняется, D-номер подтверждён», затронутые документы со статусом «не требуется».
- **Выбор меняет решение, стек или описание** — изменение по [процессу изменения](change-process.md): синхронизируются все спеки-участники, подтверждения ролей сбрасываются, проверки проходят; слишком большое — задача.
- Смена версии или технологии обновляет список технологий и Deploy.

<a id="kano"></a>

## Классы функций (Kano)

Класс определяется по нашим историям и требованиям и по тому, есть ли функция у аналогов; анкета не нужна.

| Класс | Признак | В Э6 |
|---|---|---|
| Базовая | без неё работа из Э2 не выполняется или вариант неприемлем; есть у всех аналогов | **MUST**: отсев до сравнения |
| Линейная | чем лучше, тем лучше закрыта потребность | критерий сравнения |
| Привлекательная | улучшает, но отсутствие не мешает | доп. критерий при равенстве |
| Безразличная | не закрывает нашу потребность | не берём, причина |
| Обратная | мешает работе или противоречит решению | не берём; у выбранного — отключить |

Классы смещаются со временем — факты о функциях аналогов проверяются **на дату**.

<a id="evidence"></a>

## Уровни доказательства

**А** — проверено нами (код, прототип, замер) · **Б** — первичный источник (документация, код, changelog, стандарт) · **В** — опыт практиков (статьи, обзоры, issue, отзывы) · **Г** — заявление без деталей (маркетинг, «скоро будет»).

Наличие функции — уровень Б+. Ценность — наша история или требование плюс одно из: функция у ≥ 2 аналогов; опыт практиков (В); наш прототип (А). Код и спецификация API существующей системы — уровень А.

<a id="argument"></a>

## Аргумент вывода (Тулмин)

**Утверждение** (что решили) · **Основания** (факты) · **Связка** (почему факты ведут к выводу) · **Оговорка** (насколько сильно) · **Опровержение** (когда вывод неверен: например, «если релизы прекратятся дольше 6 месяцев»).

<a id="layout"></a>

## Подача результата

«Ответ первым» (пирамида Минто). **Первая страница — презентация для заказчика на 3 минуты**, без таблиц баллов:

1. **Вопрос и ответ** одной фразой, статус Tech Radar, ссылка на решение.
2. **Микропрезентация** — до 6 слайдов ([ниже](#deck)).
3. **Почему** — 3 карточки: вывод, ключевой факт, ссылка на этап.
4. **Берём / адаптируем / не берём.**
5. **Отсеяны** (одна причина у каждого); **риски и пересмотр** (сюда же — ворота ⚠️).
6. **Путь исследования** — цепочка этапов.

Дальше — этапы Э1–Э10, каждый со строкой «**Вывод этапа.**» и воротами. **Приложение** (сворачиваемое): [карточки кандидатов](#candidate-card) — только то, чего нет в Э4; числовая сверка (необязательна; если есть — подписана «сверка, не основание»); сырые данные.

**Источники** — одна строка на источник: ссылка, дата, уровень доказательства, 3–5 слов «что взято». Описание кандидата из Э4 не повторяется. Дата — у строки или одна на раздел («обращение ГГГГ-ММ-ДД»), если все источники открыты в один день:

```
- [каталог подрядчика: продукт X](https://…) — 2026-10-13, Г, сроки запуска коробки
```

Текст: вывод — связной фразой с причиной («берём X, потому что Y»); у факта о продукте — ссылка; «нет функции» — только после проверки изданий (функция может быть в платном).

<a id="deck"></a>

### Микропрезентация

Один слайд — **один вопрос заказчика** и строка-вывод; **пропорции берутся из таблиц этапов**, а не придумываются; **без сумм баллов** (число — только количество или оценка задачи). Обязательный слайд — **«Объём доработки»**: из оценок задач в днях или порядковой шкалы Э9 («малый / средний / крупный / всё писать» = 1–4 из 4).

| Слайд | Вопрос заказчика | Откуда |
|---|---|---|
| Покрытие потребностей | кто закрывает то, что нам нужно? | Э9, по числу потребностей |
| Объём доработки | сколько придётся сделать самим? | оценки задач / шкала Э9 |
| Встраивание | что меняется в схеме? | Э7: затронутые интерфейсы, И0–И4 |
| Позиции ролей | кто за, кто против и почему? | Э8 |
| Что меняется | что будет с документами и задачами? | Э10, по статусам |

Форма — таблица слайдов (как в [шаблоне](../templates/rnd.md)) или разметка слайдов, если сборка проекта её поддерживает. Цвета, если есть: зелёный — закрывает или внесено, жёлтый — с доработкой или предложено, красный — не закрывает, синий — адаптация, серый — не требуется.

## Где искать альтернативы

**Поиск за один ход.** До поиска — список: известные кандидаты и **виды источников под G4** (≥ 5 кандидатов из ≥ 3 видов), по каждому виду — запрос. Затем все поиски одной пачкой (параллельно); второй ход — только если G4 не набран.

**Технологии и решения:**

| Источник | Что смотреть |
|---|---|
| GitHub: поиск по темам и ключевым словам | звёзды, лицензия, последний коммит за 12 месяцев, архивирован ли |
| Списки «awesome-…», CNCF Landscape | открытые проекты области |
| AlternativeTo, Product Hunt | новые продукты (за год) и аналоги известных |

| Статьи «<технология> alternatives <год>» | кандидаты, о которых не знали |
| Собственный стек проекта | что уже есть и работает |

**Продуктовые R&D** (новый продукт, потоки пользователей):

|---|---|

<a id="candidate-card"></a>

## Карточка кандидата (приложение)

Только то, чего **нет в Э4**: функции по потребностям не повторяются (они в таблицах Э3–Э4). Непроверенное — клеткой 📌 «не проверено». Для малого R&D карточку можно не вести, если всё есть в Э4 и Э7.

| Группа | Данные | Источник |
|---|---|---|
| Расширяемость | открыт ли код; лицензия и её обязательства; точки расширения (API, плагины) | репозиторий, LICENSE |
| Издания и цена | что в открытом издании, что только в платном | страница изданий и цен |
| Размещение | у себя или только облако; зависимости; ресурсы | документация по установке |
| Здоровье проекта | звёзды, контрибьюторы за 12 месяцев, релизы, реакция на issue, OpenSSF Scorecard | GitHub, scorecard.dev |
| Безопасность | известные уязвимости, модель прав | GitHub Advisories, документация |
| Совместимость | с нашим стеком (языки, БД, платформа развёртывания) | документация, прототип |

<a id="ag"></a>

## Технологии ИИ-агентов: проверка прототипом

Ценность агентной технологии подтверждается прототипом (уровень А); без прототипа статус — не выше **Trial**. Измерения: **AG1** выполнение задачи · **AG2** выбор инструментов и аргументы · **AG3** восстановление после ошибок · **AG4** связность плана · **AG5** эффективность (токены, задержка, стоимость) · **AG6** наблюдаемость и evals. Прототип: 5–10 эталонных задач на mock-LLM и реальной модели.

## Антипаттерны

| Антипаттерн | Как правильно |
|---|---|
| Критерии и веса заданы до разбора функций | критерий — результат Э6 с цепочкой |
| Итог — сумма баллов | вывод аргументом; баллы — сверка в приложении |
| Сравниваются продукты целиком | решение по каждой функции, в том числе у отсеянных |
| Обязательное свойство как взвешенный критерий | базовая функция → MUST, отсев до сравнения |
| Ценность «очевидна» | механизм ценности и доказательство |
| Первая страница — таблица | вопрос → ответ → 3 основания → перенос → риски |
| Решение оценено отдельно от схемы | встраивание по интерфейсам и хранилищам (Э7) |
| Выбор с одной позиции | спор ролей с оппонентом и «адвокатом дьявола» (Э8) |
| R&D без последствий | таблица последствий со статусами (Э10) |
| Факты по памяти | ссылка и дата; проверка изданий |
| Общая таблица критериев для всех R&D | критерии каждого R&D — из его потребностей |
| ⚠️ вместо поиска | факт, который находится поиском, — возврат, а не ⚠️ |

<a id="us-rnd"></a>

## R&D пользовательских потоков

Тот же принцип «функции аналогов → ценность → перенос», единица анализа — поток пользователя.

1. Работы (JTBD) по акторам — Э2.
2. 3–5 аналогов и их потоки: точки входа, состояния, действия людей и агентов — Э3–Э4 (источники — [продуктовые](#search)).
3. Ценность потока — Э5, как у функции.
4. **В Э6** — матрица «поток × аналог × у нас», затем отыгрыш персон и фильтр необходимости; итог — истории или осознанное «не делаем» с причиной.

**Матрица «поток × аналог × у нас»** (Э6):

| Поток (актор, работа П…) | Аналог 1 … Аналог N | У нас | Решение |
|---|---|---|---|
| строка — поток: точка входа → действие → результат | клетка: **есть** (уровень, ссылка) · **частично** — чего нет · **нет** · 📌 не проверено | **есть** · **частично** · **нет** · **история** US-… (если уже описана) | **брать** / **адаптировать** (что меняем) / **не делаем** (причина) → история |

Поток с «есть» у ≥ 2 аналогов и без «у нас» — кандидат в базовые (Kano); «не делаем» без причины недопустимо.

**Отыгрыш и фильтр** (Э6, после матрицы, до критериев): отыграть [персон](#personas) на потоках с решением «брать» и «адаптировать» — конфликты дают новые потоки или вопросы 📌; затем [фильтр необходимости](user-stories.md#7а-фильтр-необходимости): у потока есть (1) работа из Э2, (2) путь — актор, канал, данные, (3) он нужен для функции продукта. Не прошёл (1) или (2) — «не делаем»; сомнение в (3) — 📌 владельцу.

**Составной вопрос** «какие потоки + как делать» (новый продукт: состав и путь реализации) — **один R&D, два уровня**:

- Э2–Э6 — по потокам: матрица даёт состав (потоки «брать» — MUST, остальное — критерии);
- кандидаты Э4 — **пути реализации** (коробка, своя разработка, агрегатор, ничего не делать), у каждого — покрытие потоков той же матрицы;
- Э7–Э9 — выбор пути по потокам-MUST и встраиванию;
- если пути не зависят от состава потоков — два R&D: сначала потоки, затем путь.

<a id="personas"></a>

## Персоны и отыгрыш конфликтов

1. **Сущности** — участники и объекты процесса; у каждой — что **может** и что **хочет**.
2. **Персоны** — промпт персоны продукта; новые — добавить.
3. **Отыгрыш** — сыграть цель каждой персоны, искать конфликты с другими и с системой.
4. **Таблица конфликтов:** кто → что хочет → с кем конфликт → что должно произойти.
5. **Итог** — потоки, истории, требования, открытые вопросы 📌.
