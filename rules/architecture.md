# Методология архитектуры

← [Правила](README.md) · [типы документов](doc-types.md) · [формат схем](diagrams.md)

Как вести архитектуру: общую схему, страницы компонентов и блоков, раздел взаимодействия компонентов и слой поставки.

## Назначение и читатель

Архитектура отвечает на вопрос **«как устроена система и почему так»**. Читатель — тот, кто впервые видит систему: разработчик, архитектор, владелец продукта. За 10 минут он должен понять, из каких частей система, как они связаны и где читать подробности. Подробности (значения параметров, поля данных, конфиги, задачи) живут в своих вкладках — архитектура на них ссылается.

## Основа

| Практика | Что берём |
|---|---|
| [C4 model](https://c4model.com) | уровни: C1 — система в окружении, C2 — контейнеры (сервисы и хранилища), C3 — компоненты внутри, развёртывание; одна схема — один уровень |
| [arc42](https://arc42.org) | «решения» (что выбрано и почему), «сквозные концепции», «развёртывание»; ссылки на решения вместо пересказа |
| ADR ([решения](decisions.md)) | у каждого сквозного решения — D-номер и R&D |
| [Формат схем](diagrams.md) | виды схем и правила рисования (mermaid); генерируемые схемы — из источника |

## Из чего состоит

| Документ | Разделы | Источник |
|---|---|---|
| Архитектура (главная) | C1; карта (C2) — одна, второй схемой не повторяется; **взаимодействие компонентов** — сквозной сценарий по правилу [«Порядок работы и сценарии»](#how); развёртывание; поставка (сборка, реестр — вне рантайма); **сквозные решения** — таблица: решение, что выбрано (одна фраза), D, где подробно | пишется руками |
| Страница компонента (вкладка «Архитектура») | «Позиция в системе» — **путь работы**: откуда компонент получает работу и кому передаёт дальше; схема блоков (C3); «Почему так» (плюсы, минусы, расширения); «Как работает» | файл данных компонентов + `how/<компонент>.md` |
| Схема C1 компонента (вкладка «Интеграции») | компонент и соседи; стрелка — кто вызывает; подпись — I-коды | генерируется из файла данных интеграций |
| Страница блока | карточка блока ([блоки](blocks.md)) | генерируется из файла данных блоков |

**Чего нет на главной:** блоков (есть карта), расширений, плюсов и минусов (→ «Почему так» компонента), подробностей решений (→ решения и компоненты), доработок (→ задачи), терминов и типов данных (→ «Справка»).

**Чего в архитектуре нет вообще:** значений параметров и порогов (→ параметры спек), конфигов и переменных (→ Deploy), полей данных (→ «Интеграции» и «Данные»), списков доработок и статусов (→ задачи). Порядок работы одного компонента — не на главной, а в его «Как работает».

<a id="how"></a>

## Как работает: порядок работы и сценарии
`how/<компонент>.md`, раздел вкладки «Архитектура». Начинается подразделом **«Порядок работы и сценарии»** с двумя видами:

| | Порядок работы (таблица) | Сценарий (sequence-диаграмма) |
|---|---|---|
| Отвечает на вопрос | какие потоки есть у компонента и какие данные в них идут | что за чем происходит в одном сценарии, кто отвечает и что при ошибке |
| Сильное | видны **все** потоки, в том числе редкие (настройка, очистка, экспорт); коротко | точный порядок вызовов и ответов, ветки ошибок, циклы, ожидание |
| Слабое | нет порядка ответов и веток | один сценарий; больше ~15 сообщений не читается |
| Чего в нём **не** пишем | эндпоинты, методы, протоколы, пояснения | все потоки компонента; поля моделей |

**Порядок работы** — строка на поток:

| Колонка | Что указать |
|---|---|
| # | номер потока |
| Поток | что происходит, одной фразой |
| Участники | кто → кому (компоненты и блоки, без эндпоинтов) |
| Данные | имя модели или поле; без пояснений |
| I | I-код, если поток пересекает границу компонента; внутри — «—» |
| Сценарий | номер сценария, где поток показан подробно (С1, С2), или «—» |

Дополнительная колонка допустима, если она — особенность компонента.

**Сценарии** — 1–3 sequence-диаграммы по [формату схем](diagrams.md): `#### С1. <название>`; основной путь обязателен, остальные — ключевые ветки. Сообщение — вызов (`POST /path`) или модель и I-код; ответ — `-->>`; ошибки — `alt`; авторизация — один раз в `Note`.

Ниже — особенности компонента (состояния, циклы). Ссылки из «Как работает»: модель — на её контракт, стороны и протоколы — на «Интеграции», сквозной сценарий — на главную.

<a id="entity"></a>

## Тип сущности
| Тип | Что это | Обязательные документы |
|---|---|---|
| **Компонент** | единица ответственности (C2): свой контракт с соседями, можно поручить отдельной команде или агенту | полный набор вкладок |
| **Встроенный компонент** | компонент, работающий внутри другого (в его процессе, образе или контейнере) | тот же полный набор + правила [связности](#connectivity) |
| **Блок** | часть устройства одного компонента (C3), без своего контракта наружу | карточка блока ([блоки](blocks.md)) |

<a id="connectivity"></a>

## Связность компонентов
Компоненты связаны только так, как записано в источнике, и связь видна с обеих сторон.

| Правило | Проверка |
|---|---|
| Связи компонента — интерфейсы (I-коды) и размещение (хост); ручных списков связей нет | связность |
| У каждого компонента есть хотя бы один интерфейс | связность |
| Каждый переход «пути работы» — интерфейс между соседями или размещение одного в другом | связность |
| Сетевой вызов между компонентами — свой I-код, даже если вызываемое встроено в другой компонент | интеграции |

**Встроенный компонент** записывается в таблицу размещения (владелец → хост).

| Для встроенного | Что должно быть |
|---|---|
| Описание | одно — у владельца; у хоста блок ведёт на описание владельца |
| Документы | полный набор, как у отдельного компонента; у блока без своего компонента — требования, задачи, I-коды, по которым его вызывают |
| Deploy | у владельца — «в составе образа <хост>»; у хоста — упоминание встроенного |
| Карта (C3) хоста | встроенный — блок-ссылка **внутри зоны хоста**, не внешняя карточка |

## Как вести

| Когда | Шаги |
|---|---|
| Новый компонент | 1) R&D и решение D; 2) блок на C2; 3) данные компонента и блоков; 4) интеграции и данные; 5) спека, Deploy, задачи |
| Новый встроенный компонент или блок | 1) размещение; 2) описание только у владельца; 3) I-код сетевого вызова; 4) документы; 5) Deploy владельца и хоста |
| Новая связь между компонентами | 1) I-код в файле данных (стрелка = кто вызывает) и в спеках всех участников; 2) стрелка на C2 с подписью; 3) шаг во «Взаимодействии», если связь в сквозном сценарии |
| Новое сквозное решение | 1) R&D → D-номер; 2) раздел решения: что и почему кратко + ссылки; 3) последствия по цепочке |
| Изменение развёртывания или поставки | схема; детали — Deploy; значения — параметры спеки инфраструктуры |
| Устаревшее после решения | найти в архитектуре и схемах всё, что противоречит новому D, и исправить в том же изменении |

## Чек-лист качества

- [ ] На каждой схеме — один уровень C4; стрелки подписаны данными и I-кодом.
- [ ] У каждого сквозного решения есть D-номер и ссылка на R&D.
- [ ] Нет значений параметров, YAML, JSON, переменных среды, списков задач.
- [ ] Названия компонентов совпадают с навигацией и файлом данных.
- [ ] Плюсы и минусы — по каждому модулю, а не по схеме целиком.
- [ ] Каждый переход пути работы подтверждён интерфейсом или размещением.
- [ ] Ответ по архитектуре: схема + таблица блоков + расширения + плюсы и минусы по модулям.

## Проверки

- «Как работает»: нет конфигов; есть таблица порядка работы с колонками «I» и «Сценарий» без эндпоинтов и хотя бы один `sequenceDiagram`; I-коды существуют; номера сценариев совпадают.
- Связность: правила раздела выше; полный набор документов у каждого компонента.
- Архитектура: нет блоков `yaml` / `json` и таблиц значений («Порог», «По умолчанию», «Значение», «Переменная»).
- Интеграции на страницах компонентов = интерфейсы спек.

## Типичные ошибки

| Ошибка | Как правильно |
|---|---|
| Копия значений и конфигов в архитектуре расходится со спекой | ссылка на параметр спеки |
| Решение изменилось, схема — нет | исправить всё противоречащее в том же изменении |
| Отменённый вариант остался на схеме | то же |
| Порядок работы компонента в общей архитектуре | «Как работает» компонента |
