# Методика User Stories

← [Правила](README.md) · [SDD](sdd.md) · [критерии спеки](spec-criteria.md) · [R&D](rnd.md#us-rnd)

Как строить истории, чтобы они покрывали **всех пользователей и все сценарии**. Сочетает признанные практики (JTBD, анализ аналогов, карта историй, Use-Case 2.0, Example Mapping, QUS) и адаптирует их под ИИ-агентов. Истории — вход для требований: требование без истории — дефект (кроме внутренних технических).

## Итог

| Шаг | Практика | Что даёт | Чем проверяется покрытие |
|---|---|---|---|
| 0. Зачем | **Jobs-to-be-Done** | работы, ради которых компонент существует | каждая история выводится из работы |
| 0а. Как делают другие | **R&D аналогов** (потоки похожих продуктов) | потоки и точки входа, о которых не подумали | матрица «поток аналога × у нас», каждое «нет» обосновано |
| 1. Кто | **Актор — цель** (Cockburn) | все участники: люди, агенты, внешние системы, время | матрица «персона × компонент» без пустых строк |
| 2. Что делают | **Карта историй** (Patton) | хребет деятельности → шаги → истории | у каждого шага хребта есть история; MVP — «ходячий скелет» |
| 3. Над чем | **Жизненный цикл сущностей** (CRUD+) | создание, просмотр, изменение, удаление, архив, передача | матрица «сущность × операция × актор» без пустых нужных клеток |
| 4. Как бывает | **Use-Case 2.0** (Jacobson) | основной и альтернативные потоки, исключения, срезы | ≥ 1 основной + ≥ 2 альтернативных / ошибочных критерия |
| 4а. Откуда | **Точки входа** | цель достижима из всех реальных каналов | матрица «цель × точка входа» |
| 5. Что именно | **Example Mapping** (Wynne) | правила → примеры → вопросы | у правила есть пример; вопросы → вопросы спеки |
| 6. Качество | **QUS** (13 критериев) + **INVEST** | однозначные, атомарные, без конфликтов | проверка ролью «Аналитик историй» и LLM-судьёй |
| 7. Отыгрыш | **Персоны-агенты** | конфликты и забытые сценарии | таблица конфликтов: каждый — история или вопрос |
| 7а. Нужно ли | **Фильтр необходимости** | нет историй про несуществующие или ненужные пути | каждая история ссылается на работу из шага 0 |

## 0. Идея компонента и работы (JTBD)

Начинать не со списка функций, а с **идеи компонента** и **работ**, ради которых его «нанимают»: «Когда <ситуация>, я хочу <мотив>, чтобы <результат>». Каждая работа — у конкретного актора. Если из идеи работа не вытекает — переосмыслить идею: решить с обоснованием или спросить владельца (📌).

## 0а. R&D аналогов

| Поток | Аналог 1 | Аналог 2 | … | У нас | Решение |
|---|---|---|---|---|---|

Каждое «у аналога есть, у нас нет» — история или осознанное «не делаем» с причиной.

## 1. Акторы и цели

| Тип актора | Примеры |
|---|---|
| Человек — основной | пользователь, владелец процесса, ревьюер |
| Человек — обеспечивающий | администратор, эксплуатация, безопасность, QA |
| Агент | агент-исполнитель, агент-ревьюер |
| Система | соседние сервисы, внешние API |
| Время | расписание, сроки хранения, таймауты |

Для каждого актора — цели; каждая цель → минимум одна история.

## 2. Карта историй

Хребет деятельности → шаги → истории по приоритету (MVP — «ходячий скелет», затем этапы). Карта строится по сквозному процессу и по каждому компоненту. Пустая клетка под шагом хребта — дыра.

## 3. Жизненный цикл сущностей

| Операция | Вопрос |
|---|---|
| Создать / Импортировать | кто создаёт, из чего, с какой проверкой |
| Посмотреть / Найти | кто видит, где, какие фильтры |
| Изменить / Версия | кто меняет, когда вступает в силу, что с активными процессами |
| Удалить / Архивировать | что со ссылками и историей |
| Передать / Сменить владельца | кому, с какими правами |
| Истечь по сроку | что удаляется автоматически |

## 4. Потоки истории (Use-Case 2.0)

- **Основной поток** — самый простой путь к цели.
- **Альтернативные потоки** — другой путь к той же цели.
- **Исключения** — нет прав, нет данных, зависимость недоступна, лимит, таймаут, конфликт.

Минимум: 1 основной + 2 альтернативных или исключения. Срез — часть потоков, которую можно сделать и проверить отдельно; срезы попадают в разные задачи.

## 4а. Точки входа

Интерфейс (экраны, настройки), комментарии и упоминания, чат, уведомления, автоматизация и расписание, API. Для каждой цели — все реальные точки входа; история или критерий на каждую, где поведение отличается.

## 5. Example Mapping

Правила (бизнес-ограничения) → примеры на каждое правило → вопросы без ответа. Примеры становятся сценариями требований; вопросы — строками вопросов спеки.

## 6. Качество (QUS + INVEST)

| Группа | Критерии |
|---|---|
| Синтаксис | корректная форма «Как <роль>, я хочу <цель>, чтобы <польза>»; атомарность; минимальность |
| Семантика | концептуальная точность; ориентация на проблему (без «как сделать»); однозначность; бесконфликтность |
| Прагматика | полное предложение; оцениваемость; уникальность; единообразие; независимость; полнота набора |

## 7. Адаптация под ИИ-агентов

- **Персоны-агенты.** Каждая персона — промпт; агент отыгрывает её цель и ищет конфликты.
- **Многоагентный сбор требований:** «аналитик» спрашивает, «заказчик» (персона) отвечает, «QA» оценивает по QUS, «владелец» приоритизирует.
- **LLM-судья.** Сгенерированные истории проверяются отдельным проходом по QUS; спорное — человеку.
- **Агент — тоже актор:** что получает (задание, контекст, права), что делает, что возвращает, что при отказе.
- **Человек утверждает.** Итог генерации — предложение; историю утверждает владелец продукта.

## 7а. Фильтр необходимости

Три вопроса: (1) из какой работы шага 0 следует история; (2) существует ли путь (актор, канал, данные); (3) нужна ли она для функции компонента. Нет ответа на (1) или (2) — история не пишется. Сомнение в (3) — вопрос владельцу, а не история «на всякий случай».

## 7б. Сквозная трассировка

История точки входа проходит через истории других компонентов. Для неё — цепочка историй по порядку потока и **логическая конечная точка** (что видит пользователь, в каком состоянии остаётся объект). Тупик без конечной точки — дефект.

## 8. Проверки покрытия

- матрица «персона × компонент»: пустые клетки видны;
- истории с менее чем 3 критериями приёмки;
- истории без требований, пользовательские требования без истории;
- ссылка истории ведёт на само требование (якорь), а не на спеку целиком;
- у каждого процесса (BPMN) есть хотя бы одна ветка ошибки;
- у сквозных цепочек есть конечная точка.

## Что ещё бывает на вкладке

Раздел «процесс глазами пользователя»: схема процесса, что пользователь видит и где, ссылки на требования. **Нельзя:** где хранится сущность (→ Данные), правила переходов и лимиты (→ спека). Правило, которого нет в спеке, — сначала требование, потом ссылка.

## Процесс

0. Идея компонента → работы → R&D потоков аналогов.
1. Акторы, карта, сущности, точки входа.
2. Для каждой цели — история с потоками и примерами.
3. Отыгрыш персон → новые истории и вопросы.
4. Проверка качества и фильтр необходимости отдельным проходом.
5. Требования: из примеров — сценарии, из правил — требования; связь история ↔ требование.
6. Пройти с пользователем по сценариям, закрыть вопросы.
