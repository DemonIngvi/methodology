# Типы документов и вкладки

← [Правила](README.md) · [структура](structure.md) · [процесс изменения](change-process.md)

Строка на тип документа. Колонку «Где» проект заполняет шаблонами своих путей — по ней инструмент `doc route` узнаёт тип файла и выдаёт выжимку правил. Пути ниже — пример раскладки.

| Тип | Где (пример) | Обязательные разделы | Правила | Синхронизировать | Методология |
|---|---|---|---|---|---|
| **Главная / архитектура** | `architecture.md` | C1, карта (C2), взаимодействие компонентов, развёртывание, сквозные решения (что и почему + ссылки) | только то, что не принадлежит одному компоненту; без значений параметров, конфигов, переменных и списков доработок | решения, спеки, страницы компонентов | [архитектура](architecture.md) |
| **README** | `README.md` | что за система, ссылки на разделы | — | главная | [структура](structure.md#support) |
| **Формат схем** | `rules/diagrams.md` | виды схем и правила рисования; формат ответа по архитектуре | — | — | [архитектура](architecture.md) |
| **Как работает** | `how/<компонент>.md` | «Порядок работы и сценарии»: таблица потоков и 1–3 sequence-диаграммы; затем состояния, циклы | данные — именами моделей; конфигов нет | модели, взаимодействие на главной | [архитектура](architecture.md#how) |
| **Страница блока** | генерируется из файла данных блоков | карточка блока, заполненность, подтверждения | параметры — имена из спеки; существующее во внешней системе — по её коду | спека, технологии | [блоки](blocks.md) |
| **Данные и интеграции** | файл данных интеграций, моделей, таблиц | интерфейсы, модели, таблицы, политика хранения | единственный источник; страницы генерируются | спеки-участники, каталог API | [данные](data.md) |
| **Интеграции** (вкладка) | `api/<компонент>.md` | схема C1, карточки интеграций, контракты, эндпоинты со структурой | «✅ есть» — только если путь есть в спецификации API работающей системы | файл данных, спецификация API | [API](api.md) |
| **Deploy** | `deploy/<компонент>.md` | образы, запуск, переменные и секреты, конфигурация (генерируется), сборка и поставка, проверка после развёртывания | только развёртывание и настройка; порядок работы — в «Как работает» | технологии, параметры спеки | [Deploy](deploy.md) |
| **Spec** | `specs/<cap>/spec.md` | Purpose, требования, сценарии | [критерии полноты](spec-criteria.md) | параметры спеки, трассировка, «Как работает», истории, задачи | [SDD](sdd.md) |
| **Параметры и интерфейсы спеки** | `specs/<cap>/interfaces.md` | уровни конфигурации, параметры, хранилища S, интерфейсы I, FMEA, нагрузка и развёртывание | коды S и I — единые для всех спек | spec, файл данных, «Как работает», Deploy | [SDD](sdd.md), [данные](data.md) |
| **Трассировка (RTM)** | `specs/<cap>/traceability.md` | требование → обоснование → задача → сценарии | разрывы явно; без задачи — решение «не в MVP» | spec, задачи, R&D | [критерии](spec-criteria.md) |
| **Открытые вопросы спеки** | `specs/<cap>/open-questions.md` | ID, вопрос, тип ❓ / 📌, блокирует ли, источник, кто решает | закрытый вопрос — удалить и записать решение в решения / спеку | готовность спеки, ревью, задачи | [ревью](review.md) |
| **Подтверждения спеки** | `specs/<cap>/approvals.md` | требование, роль, кто, 👤 / 🤖, дата, решение, комментарий | роль меняет только свою строку | готовность спеки | [подтверждения](approvals.md) |
| **Решения** | `design.md` | контекст, решения (D-номера), риски, открытые вопросы | у решения — альтернативы и ссылка на R&D | R&D, архитектура | [решения](decisions.md) |
| **R&D** | `rnd/<тема>.md` | первая страница, этапы Э1–Э10 со строкой «Вывод этапа» и воротами (✅ / ⚠️ с 📌), приложение, источники (ссылка, дата, уровень) | факты с источником и датой; не подгонять баллы | решения (D-номер), сводка последствий | [R&D](rnd.md) |
| **User Stories** | `stories/<компонент>.md` | роли, процесс (BPMN) с ветками ошибок, истории «Как… хочу… чтобы…», критерии приёмки, связанные требования | каждая история ссылается на требования | spec, трассировка, задачи | [User Stories](user-stories.md) |
| **Задача** | `tasks/<N.M>-<slug>.md` | оценки, закрывает требования, зачем, что сделать, приёмка, INVEST, декомпозиция (2–8 ч), что проработать | ссылается на требование спеки | Roadmap, сводная таблица | [задачи](tasks.md) |
| **Roadmap / сводная таблица / бэклог** | `ROADMAP.md`, `TASKS.md`, `BACKLOG.md` | этапы и итоги; сделано → нужно; что отложено и почему | итоги пересчитываются; ссылки на документы задач | задачи | [задачи](tasks.md) |
| **Технологии** | `TECHNOLOGIES.md` | технология, назначение, версия, лицензия, источник, кольцо радара, R&D | новая технология для выбора между альтернативами — с R&D | R&D, решения | [структура](structure.md#support) |
| **Ревью** | `reviews/<дата>-<тема>.md` | роли, замечания по спекам, сквозные замечания, итог | статусы ✅ / ❓ / 📌 | спеки, задачи | [ревью](review.md) |
| **Замечания компонента** | `reviews/findings/<компонент>.md` | таблица замечаний ролей | ID не переиспользуется | реестр подтверждений | [ревью](review.md#findings) |
| **Журнал отклонений** | `rules/deviations.md` | что нашли → почему → правило и проверка | у строки — правило или проверка | процесс изменения | [ревью](review.md) |
| **Правила и методологии** | `rules/` | назначение, основа, из чего состоит, как вести, чек-лист, проверки, типичные ошибки | правка — сначала инструменты ([изменение правил](change-process.md#rules-change)) | инструменты, документы типа | [процесс изменения](change-process.md) |

## Вкладки и их наполнение
Каждая вкладка отвечает на **свой** вопрос. Факт живёт в одной вкладке, остальные ссылаются на неё ([один источник](change-process.md#single-source)). Если тянет написать во вкладке то, что относится к другой, — ставим ссылку.

| Вкладка | Отвечает на вопрос | Обязательно | Чего здесь нет → где это |
|---|---|---|---|
| **Архитектура** | из чего состоит, почему так и как работает | схема блоков, «Почему так», «Как работает» | параметры → Deploy («Конфигурация»); стыки и контракты → Интеграции; хранилища → Данные; процесс пользователя → User Stories; требования → Спеки |
| **Блоки** (внутри «Архитектуры») | что делает блок и на чём сделан | карточка блока | значения параметров → спека |
| **User Stories** | кто и зачем пользуется, как проходит процесс пользователя | истории, процесс, критерии приёмки | требования → Спеки; работа системы → «Как работает» |
| **Спеки** | что компонент обязан делать | требования со сценариями; параметры, хранилища, интерфейсы, нагрузка, FMEA; RTM; вопросы; подтверждения | порядок работы → «Как работает»; поля данных → Интеграции / Данные |
| **Задачи** | что сделать, сколько стоит, как принять | оценки, требования, приёмка, декомпозиция | зачем так устроено → R&D, решения |
| **Интеграции** | с кем связан, через что, что передаётся, какие вызовы | C1 (стрелка — кто вызывает), карточки, контракты, эндпоинты со структурой | хранилища → Данные |
| **Данные** | что компонент хранит и как | хранилища, ER, таблицы полей, индексы, срок, очистка, миграции | контракты обмена → Интеграции; значения сроков → параметры спеки |
| **Deploy** | как собрать, развернуть, настроить | образы, запуск, переменные и секреты, конфигурация, сборка, проверка | порядок работы → «Как работает»; значения параметров → спека |
| **R&D** | почему выбрано именно так | исследование, последствия Э10 | решение → решения (D) |
| **Замечания** | что нашли роли и как закрыто | таблица замечаний со статусами | — |

## Расхождения страниц с правилами
Периодически каждая страница сверяется со своей строкой таблицы и методологией. Расхождения — таблицей на решение, без немедленных правок:

| Тип | Что расходится | Править | Как |
|---|---|---|---|

«Править» — где устранять причину: **методология**, если страница ошибается, потому что правило молчит или само задаёт дубль; **страница**, если правило ясное, а страница от него отстала. Причина большинства расхождений обычно — в методологии.
