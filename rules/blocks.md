# Методология блоков

← [Правила](README.md) · [архитектура](architecture.md#entity) · [подтверждения](approvals.md) · [шаблон карточки](../templates/block-card.md)

Как вести блоки — части устройства компонента (C3): карточку блока и его страницу.

## Назначение и читатель

Карточка отвечает на вопросы **исполнителя, который берётся сделать блок**: что сделать, как это выглядит или вызывается, с чем связано, что хранит, как настраивается, по каким требованиям и задаче, что при сбое. Нет ответа — блок не готов к реализации, и это видно на его странице.

## Основа

| Практика | Что берём |
|---|---|
| [C4 model](https://c4model.com), уровень C3 | блок — часть одного контейнера, без своего контракта наружу |
| Definition of Ready | блок готов, когда карточка полная, открытых вопросов нет, роли подтвердили |
| Инвентаризация «как есть» | то, что уже существует (в форке, во внешней системе), описывается по коду, а не по памяти |

## Блок, встроенный блок, компонент

| | Блок | Встроенный блок | Компонент |
|---|---|---|---|
| Свой контракт наружу (I-код) | нет | вызывают по сети | да |
| Документы | карточка | карточка + I-коды + Deploy хоста | полный набор вкладок |

Если у блока появляется свой контракт с соседями и его можно поручить отдельно — это уже компонент: сначала решение, потом перенос.

## Карточка

| Поле | Вопрос исполнителя | Как заполнять | Проверка |
|---|---|---|---|
| Что делает | что блок делает | 2–4 пункта, глаголом | есть |
| Технология | на чём сделан | технология и версия — из списка технологий | есть |
| Истории | для кого и в каком процессе | коды историй | история существует |
| Входы и выходы | откуда приходит работа и кому отдаёт | `«←» / «→», с кем, что: модель или I-код` | I-код существует |
| Данные | что читает и пишет | **имена таблиц** (не коды хранилищ), «чтение» / «запись»; чужая таблица — с пометкой владельца; у блока без таблиц (прокси, хранилище файлов) — строка `нет: <почему>` (поле заполнено) | таблица есть в модели данных |
| Параметры | как называются настройки | имя **как в конфиге** из таблицы параметров спеки; у блока без настроек — строка `нет: <почему>` (поле заполнено) | имя есть в спеке |
| Требования | какие требования выполняю | R-коды всех требований, на которые опираются операции, экраны и сбои | требование существует |
| Задачи | по какой задаче делаю | номера задач | задача существует |
| При сбое | что при отказе блока и зависимостей | поведение + ссылка на FMEA | есть |
| По виду (ниже) | как выглядит или вызывается | см. «Вид блока» | есть |
| Почему так | почему так | 1–2 предложения + R&D | есть |

### Вид блока

| Вид | Поле | Что в нём |
|---|---|---|
| Интерфейс (UI) | экраны | путь в интерфейсе, что на нём (поля, действия), статус `есть` / `доработка` / `новое`, файл в коде, история; у каждого действия — операция API |
| Сервис или модуль | операции | эндпоинт или функция, кто вызывает, I-код или «внутри» |
| Хранилище, конфиг | схема | ссылка на «Данные» или на конфиг |

## Как вести

| Когда | Шаги |
|---|---|
| Новый блок | 1) строка в схеме C3; 2) карточка со всеми полями; 3) нет требования — сначала требование ([приёмка задачи](change-process.md#task-intake)) |
| Экран с действием | у каждого действия — операция API; нет эндпоинта — сначала строка в каталоге API |
| Экраны из задач | экран, который делает задача блока, — строкой в «экранах» |
| Блок уже существует | экраны и операции — **инвентаризация по коду**: путь, файл, что есть; доработку отмечать с требованием |
| Есть выбор, как сделать | R&D → решение D → карточка; до решения — открытый вопрос в спеке |
| Неизвестно, как устроено | не придумывать: код, спецификация API, решения; нет — открытый вопрос |
| Изменилась карточка | подтверждения блока сбрасываются ([подтверждения](approvals.md)) |

## Готовность к реализации
Блок готов, когда: карточка заполнена полностью, по требованиям блока нет открытых вопросов, роли блока подтвердили карточку. На странице блока — заполненность и значки подтверждений.

## Чек-лист

- [ ] Тип и вид блока указаны.
- [ ] Каждое поле отвечает на свой вопрос; ссылки существуют.
- [ ] Экраны и операции — по коду или по решению D, не по памяти.
- [ ] Параметры — имена из спеки.
- [ ] Открытых вопросов по требованиям блока нет или они названы.

## Проверки

Ссылки карточки существуют (I-коды, таблицы, требования, задачи, истории); заполненность карточек (`doc blocks`); lint: экраны «новое» / «доработка» без эндпоинта, коды хранилищ вместо таблиц; проверяет lint также: требование и таблица, названные в карточке (операции, сбои, технология), — в её «Требованиях» и «Данных»; закрытый или несуществующий открытый вопрос в карточке; эндпоинт с экрана есть в каталоге API — плагином проекта; проверяющий по роли — реализуемость и открытые вопросы. Карточка может жить в YAML по единице ([данные](data.md#yaml)) — те же проверки.
