# Методология интеграций и API

← [Правила](README.md) · [данные и интеграции](data.md)

Как вести вкладку «Интеграции» компонента: схему C1 и карточки интеграций (генерируются из файла данных), таблицу эндпоинтов `api/<компонент>.md`, примеры моделей в каталоге API.

## Назначение и читатель

Отвечает на вопрос **«какие вызовы есть, что в них передаётся и что из этого уже существует»**. Читатель — разработчик компонента и тот, кто оценивает объём доработок существующей системы.

## Основа

| Практика | Что берём |
|---|---|
| OpenAPI 3 | структура существующих эндпоинтов — из спецификации работающей системы |
| [Zalando RESTful API Guidelines](https://opensource.zalando.com/restful-api-guidelines/), [Google AIP](https://google.aip.dev) | ресурсный путь, метод по смыслу, явные коды ответа |
| Трассировка | у эндпоинта — истории, требования, I-код |

## Из чего состоит

| Колонка или раздел | Что указать |
|---|---|
| Метод, путь | как в коде; параметры пути — `:id`; **одна строка — один путь**: доработка существующего пути — статус 🛠 на этой же строке, а не отдельная строка с пометкой поля в пути |
| Статус | ✅ есть — путь есть в спецификации API работающей системы (или в её коде — с указанием файла); 🛠 доработка — путь есть, меняем тело или поведение; 🆕 новое |
| Что делает | одной фразой; модели — именами |
| Кто вызывает | компонент и способ доступа |
| Истории, требования, I | ссылки на US, R и I-код |
| Структура запросов и ответов | генерируется из спецификации API и / или из записи о доработке в файле данных |
| Пример модели | каталог API, раздел `### <Модель>` — единственное место примеров |

## Как вести

1. Новый или изменённый эндпоинт — строка в таблице компонента; статус — по спецификации API, не по памяти. Меняется существующий путь — правится его строка.
2. У **каждого** эндпоинта, который меняет данные (POST / PUT / PATCH / DELETE), в любом статусе — не только у нового и доработанного — **ответы-ошибки** из сценариев отказа требований (403 — нет права, 404, 409 — состояние не позволяет).
3. Карточка интеграции описывает поведение сейчас; то, что появится после доработки, — с пометкой «после доработки (R-…)».
4. Нет в спецификации API или доработка — запись о структуре: запрос, ответ, заметка.
5. Новая модель — по [методологии данных](data.md); пример — в каталоге.
6. Обновилась существующая система — повторный импорт спецификации API, затем проверки.

## Чек-лист качества

- [ ] «✅ есть» — только для путей из спецификации API или кода со ссылкой на файл.
- [ ] В колонке «путь» — только путь; у пути одна строка.
- [ ] У всех изменяющих эндпоинтов (POST / PUT / PATCH / DELETE), в том числе ✅ есть, — коды ошибок; «ошибки: —» не годится (проверяет lint).
- [ ] У каждого эндпоинта есть структура запроса и ответа.
- [ ] Пример модели содержит только поля модели (точные имена).
- [ ] У эндпоинта есть требование и I-код.

## Проверки

**Проверяет lint:** у всех изменяющих эндпоинтов каталога — коды ошибок (в проекте правило подключается плагином, пример — `endpoint-errors` в [house.py](../examples/minimal/tools/doc_plugins/house.py)); роли это не повторяют.

Структура у каждого эндпоинта; в колонке пути нет пометок полей; ключи примеров = поля моделей; статус ✅ = путь в спецификации API.

## Типичные ошибки

| Ошибка | Как правильно |
|---|---|
| Ответ описан по памяти и расходится с работающей системой | по спецификации API или коду |
| Пример JSON с полями, которых нет в модели | пример только из полей модели |
