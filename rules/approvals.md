# Подтверждения ролями

← [Правила](README.md) · [роли](roles.md) · [проверяющий по роли](../agents/doc-reviewer.md) · [шаблон реестра](../templates/approvals.md)

Документ считается принятым, когда его подтвердили **все роли, которые отвечают за его тип**. Подтверждение — ответ роли на свой вопрос. Читатель — владелец продукта и исполнитель: по значкам видно, можно ли опираться на документ.

## Основа

| Практика | Что берём |
|---|---|
| Ревью по ролям (RACI, approver) | у каждого типа документа — список подтверждающих ролей |
| Definition of Ready | документ готов, когда все его роли подтвердили |
| Версия под подтверждением | решение относится к конкретному тексту: текст изменился — решение сбрасывается |

## Роли и буквы

Значок роли — круг с буквой: зелёный ✓ — подтвердил, красный ✕ — отказ (причина в комментарии), серый — ждёт.

| Буква | Роль | Вопрос |
|---|---|---|
| **В** | Владелец продукта | что важно, сколько стоит, что выбрать |
| **А** | Архитектор | где живут данные, как связаны модули, как развёртывается |
| **Р** | Разработчик | реализуемо ли так, как написано |
| **Т** | Тестировщик | как проверить каждое утверждение |
| **И** | Аналитик историй | кто что делает и что может пойти не так |
| **П** | Пользователь | решает ли это мою задачу |
| **Н** | Администратор (настройки) | понятны ли настройки |
| **Д** | DevOps-инженер | как развернуть, обновить, восстановить |
| **Б** | Безопасность | где утечка, лишние права, лицензионный риск |
| **С** | Инженер сборки и поставки | как собрать и откуда взять |

## Кто подтверждает какой документ

| Тип документа | Роли |
|---|---|
| Главная / архитектура | А, В |
| Архитектура компонента | А, Р |
| Блок | А, Р, Т |
| Интеграции | А, Р, Т |
| Данные | А, Р, Д |
| Deploy | С, Д, Б |
| User Stories | И, П, В |
| Задача | Р, Т, В |
| R&D | В, А |
| Решения | В, А |
| Методология | В, А |
| Спека | по требованиям (ниже); значок спеки — сводка по требованиям |

Эта таблица — источник для инструмента подтверждений; при её изменении — сначала инструмент ([изменение правил](change-process.md#rules-change)).

## Подтверждение требований
| Требование | Роли |
|---|---|
| Конфигурация | по [виду спеки](sdd.md#kinds) |
| Хранилища данных | Архитектор, DevOps-инженер |
| Интерфейсы обмена | Архитектор, Разработчик |
| Поведение при отказах | DevOps-инженер, Тестировщик |
| Нагрузка и производительность | DevOps-инженер, Тестировщик |
| Развёртывание | DevOps-инженер |
| Функциональное | Аналитик историй, Тестировщик и роли персон связанных историй |
| Требования к ограничениям агента, песочнице, правам | + Безопасность |

Подтверждения требований — в `approvals.md` рядом со спекой: требование, роль, кто, 👤 / 🤖, дата, решение ✅ / ❌ / ⏳, комментарий. Подтверждение человеком (👤) нужно для решений 📌 и для выпуска.

## Как ставится решение

1. Инструмент добавляет в реестр строку ⏳ для каждой пары «документ × роль».
2. Роль проверяет документ по своему вопросу и методологии его типа. Агент-роль — [проверяющий](../agents/doc-reviewer.md); человек — сам.
3. Решение — командой `approve <страница> <буква> ok|no "<комментарий>"` (агент — 🤖; человек — с флагом `--human`). Отказ — всегда с причиной и ссылкой на то, что исправить.
4. Текст изменился — решение сбрасывается в ⏳ с пометкой «текст изменён после решения» (в реестре хранится версия — хеш текста).
5. Что ждёт роли — `review-queue <буква>`.

**Честность:** 🤖 и 👤 различаются в реестре; агент не ставит 👤; 🤖 ✅ — только за выполненную проверку своей роли, не массовой отметкой по типу.

## Экономная проверка
Проверка ролями дорогая (на проверку одного крупного компонента всеми ролями может уйти около миллиона токенов). Порядок, который её удешевляет:

Расход: см. [пакетная проверка](token-costs.md#review-batch), [проверка пакетом на роль](token-costs.md#review-pack), [перевод отказов в lint](token-costs.md#lint-conversion) на странице «Расход токенов».

| Правило | Как |
|---|---|
| Сначала автоматика | `check` и `lint` до ролей; роли не ищут то, что ловит инструмент. Повторяющееся замечание ролей — повод для новой проверки в lint |
| Пачка — основной режим | `review-batch <компонент> [--max 30]`: один файл с компактными карточками всех ⏳-страниц компонента для всех их ролей (карточка ≤ 2500 символов, блок и единица данных ≤ 1500 — лимиты в конфиге), вопросы ролей и правило; инструмент печатает символы и оценку токенов и предупреждает, если lint компонента не пуст |
| Пачка: ответ | агент читает пачку один раз, решает за все страницы и роли, пишет **один** JSON `[{"page", "role", "ok", "comment"}]` и применяет его `approve-batch <файл.json>` — одним захватом блокировки реестра; неизвестная пара — ошибка, и реестр не меняется; в источники — не больше 2 раз на пачку |
| Пачка: цель | ~1–1,5 тыс. токенов на документ за все его роли (против 4–7 тыс. на пару «документ × роль» при пакете на роль); факт против цели — в [журнале расхода](token-costs.md#review-batch) |
| Пакет вместо поиска (запасной) | документ вне компонента или повторная проверка одного отказа: агент читает **один файл** `review-pack <страница> <буква>`: страница, вопрос роли, чек-лист методологии типа, требования страницы, открытые вопросы, прежние замечания, lint; в источники — только за фактом, которого в пакете нет |
| Только блокирующее | отказ — если без исправления нельзя ответить на вопрос роли; у замечания — факт-источник (файл, строка кода, требование); не больше 3 на документ; мелочь без последствий не записывается |
| Повторная — по изменённому | после правок роль проверяет закрытие своих прежних замечаний и изменённые разделы, а не документ заново |
| Несколько ролей — один проход | пачка компонента — сразу за все роли всех его документов; в запасном режиме — один агент на документ за все его роли, а не агент на роль по всем документам |
| Модель | проверяющим агентам — модель попроще; основной агент сводит решения и разбирает замечания |
| Разбор замечаний | перед правкой каждое замечание проверяется по источнику: безосновательное — «отклонено» с причиной; затем — что закрывается правилом методологии; правка документов — последней |

## Готовность документа

Документ готов, когда все его роли — ✅. Блок готов к реализации, когда документ готов, карточка заполнена и открытых вопросов нет ([блоки](blocks.md#ready)).

## Чек-лист

- [ ] У каждого типа документа есть роли.
- [ ] Отказ содержит причину и что исправить.
- [ ] 🤖 и 👤 не смешаны.

## Проверки

Проверяет lint (`lint`) до ролей — роль не отказывает за то, что он ловит: требования задачи покрыты приёмкой, сумма подзадач в диапазоне оценки, ссылки только на открытые вопросы, FMEA ↔ сценарий отказа, RTM ↔ спека, ID в карточке блока ↔ её поля «Требования» и «Данные», миграции в Deploy компонента с данными; проектные правила — плагином.

Строки ⏳ для обязательных пар; сброс по изменённому тексту; удаление строк по удалённым документам; значки на странице; сводная таблица «документ × роли».
