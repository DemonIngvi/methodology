# Методология ревью и замечаний

← [Правила](README.md) · [подтверждения](approvals.md) · [журнал отклонений](deviations.md) · [шаблон замечаний](../templates/review-findings.md)

Как проводить ревью документов (`reviews/`) и вести замечания проверки ролями.

## Назначение и читатель

Ревью отвечает на вопрос **«всё ли верно, связано и понятно»**; журнал отклонений — **«почему документы разошлись и что не даст этому повториться»**. Читатель — владелец продукта и тот, кто будет менять правила.

## Основа

| Практика | Что берём |
|---|---|
| Ревью по ролям ([роли](roles.md)) | аналитик — полнота поведения; техлид — реализуемость и отказы; архитектор — границы и данные; безопасность — права и утечки |
| [Google Engineering Practices: code review](https://google.github.io/eng-practices/review/) | замечание конкретное, с местом и предложением; не блокировать за вкус |
| Анализ первопричин (5 почему) | у отклонения — причина появления, а не только исправление |
| [Два читателя](dual-read.md) | понятность моделей, интеграций и имён |

## Из чего состоит

| Документ | Разделы |
|---|---|
| Ревью `reviews/<дата>-<тема>.md` | роли; таблица замечаний: ID, спека, что не так, предложение, тип (❓ вопрос, 📌 решение владельца, ✅ исправлено); сквозные замечания; итог |
| Протокол двух читателей | объект, ответ читателя 1, читателя 2, вердикт, что исправлено |
| [Журнал отклонений](deviations.md) | номер, дата, что нашли, почему появилось, правило и проверка |

## Замечания проверки ролями
Отказы и замечания ролей ([подтверждения](approvals.md)) по документам компонента собираются в `reviews/findings/<компонент>.md` — вкладка компонента «Замечания».

| Колонка | Что указать |
|---|---|
| № | `Z-<КОД>-<N>`, не переиспользуется |
| Документ | страница из реестра подтверждений |
| Роли | буквы ролей, которые нашли |
| Отклонение | одной фразой, факт с источником |
| Как закрыть | **правка** документа · **требование** (сценарий в спеке) · **вопрос** (вопросы спеки) · **R&D** → решение D · **владелец** (решение продукта) |
| Где | файл и раздел, куда вносится |
| Методология | **да → <методология и что добавить>**, если замечание можно было предотвратить правилом или проверкой; **нет — проверка ролью**, если это суждение по существу |
| Статус | ⏳ открыто · ✅ закрыто (что сделано) · 📌 ждёт владельца |

Порядок:

1. Проверка ролями → решения в реестре подтверждений.
2. Замечания — в файл компонента (повторы между ролями объединяются).
3. Разбор: каждое замечание проверяется по источнику; безосновательное — «отклонено» с причиной.
4. Закрытие каждого по своему пути (правка, требование, вопрос, R&D) — [массовыми партиями](change-process.md#bulk).
5. Всё с «Методология: да» — правило и проверка в методологию (сначала инструменты).
6. Повторная проверка ролями изменённых документов (их решения сброшены).

## Как вести

1. У каждого замечания — ID и спека. **«Ни к чему не относится» — признак ошибки границ:** искать существующее требование.
2. Замечание ❓ / 📌 — строка в вопросах спеки; исправленное — в источнике.
3. Нашли расхождение — строка в журнале: сначала причина, потом правило; правило вносится в `rules/` вместе с проверкой, где это возможно.
4. Правило без проверки — временное: задача на проверку.
5. Повторяющееся замечание ролей — повод для новой автоматической проверки (lint).

## Чек-лист качества

- [ ] У замечания есть спека и место.
- [ ] У отклонения указана причина появления, а не только факт.
- [ ] Правило внесено в `rules/`; проверка — в инструментах.

## Проверки

Готовность спек учитывает открытые замечания ревью (потолок 90); открытые вопросы снижают готовность ([критерии](spec-criteria.md#6-процент-готовности)).

## Типичные ошибки

| Ошибка | Как правильно |
|---|---|
| Сквозные замечания ревью не попали в спеки | у замечания — спека; ❓ / 📌 → вопросы спеки |
| Исправление без правила — то же расхождение повторилось в другом месте | причина → правило → проверка |
