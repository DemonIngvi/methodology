# AGENTS.md — как агенту работать с документацией

Инструкции для любого ИИ-агента (Claude Code, Codex, Cursor, Gemini, Copilot) и человека. Подключите этот файл к проекту вместе с инструментом `tools/doc` ([установка и команды](tools/README.md#install); на Windows — `python tools/doc …`). Без инструмента каждый шаг выполняется вручную по таблицам в [rules/](rules/README.md) — колонка «Вручную» ниже.

<a id="task-entry"></a>

## Тип задачи → читай только сценарий

Сначала определи тип задачи и читай **только** его сценарий и то, на что он ссылается. **README, остальные разделы этого файла (кроме [«Безопасность»](#security)) и полные правила `rules/` для таких задач не читать** — сценарий сам называет нужные разделы.

| Тип задачи | Читай только | Не читай |
|---|---|---|
| R&D (выбор технологии, подхода, состава потоков, новый продукт) | [skills/doc-rnd.md](skills/doc-rnd.md) + [templates/rnd.md](templates/rnd.md) + нужные якоря [rules/rnd.md](rules/rnd.md) по карте сценария | README, `rules/rnd.md` целиком, остальные правила |
| правка документа | [skills/doc-edit.md](skills/doc-edit.md) | README, `rules/` целиком |
| данные: интеграции, модели, таблицы, эндпоинты, блоки, истории (YAML по единице) | [skills/doc-data.md](skills/doc-data.md) | README, `rules/` целиком, страницы и файлы данных целиком (читать `tools/doc unit <ID>`) |
| двойное чтение (понятность двумя читателями) | [skills/doc-dual-read.md](skills/doc-dual-read.md) | README, `rules/` целиком |
| подтверждение документов ролями | [agents/doc-reviewer.md](agents/doc-reviewer.md) — пачка компонента | README, `rules/` целиком, страницы целиком (карточки — в пачке) |

Задача не подходит ни под один тип — дальше по этому файлу.

## Правило в момент правки — инструмент, а не чтение всех правил

Правил много. **Не читай `rules/` целиком** — получай выжимку для файла, который правишь.

| Когда | Команда | Вручную |
|---|---|---|
| перед правкой файла | `tools/doc route <файл>` — тип документа, что обязательно, чего нельзя, где источник, методология, что синхронизировать | строка типа в [doc-types.md](rules/doc-types.md) |
| файл генерируется? | `tools/doc pre <файл>` — если да, называет источник: правь его | колонка «Генерируется» в [structure.md](rules/structure.md) |
| после правки | `tools/doc post <файл>`, `tools/doc check` — все проверки за секунды | чек-лист методологии типа; `python tools/mdlinks.py .` |
| пробелы методологий | `tools/doc lint [компонент]` — нестрогие проверки, коммит не блокируют | «Проверки» в методологии типа |
| что править дальше | `tools/doc next <файл>` — следующие документы по графу и методология каждого | [doc-graph.md](rules/doc-graph.md) |
| переименовать документ | `tools/doc move <старый> <новый>` — файл и все ссылки сразу | [правило](rules/change-process.md#links) |
| подтвердить документы ролями | промпт [agents/doc-reviewer.md](agents/doc-reviewer.md); основной режим — `tools/doc review-batch <компонент>` → один JSON → `tools/doc approve-batch <файл.json>`; запасной — `tools/doc review-pack`, `tools/doc approve`; очередь — `tools/doc review-queue` | [подтверждения](rules/approvals.md#economy): карточки из страниц, решения — строки реестра |
| данные (YAML по единице) | `tools/doc unit <ID>` — карточка единицы и «связано: …»; `tools/doc yaml-check [путь]`, `tools/doc yaml-fmt [путь]` | файл единицы; схема вида — `[[data.kinds]]` конфига ([правило](rules/data.md#yaml)) |
| расход токенов | `tools/doc cost add <процесс> <токены> <единиц> <единица>`, `tools/doc cost` — замер против ожидания, допуск ±2× | строка журнала ([как замерять](rules/token-costs.md#measure)) |
| статус замечания | `tools/doc finding <компонент> <ID> ok\|wait\|owner "<что сделано>"` | [замечания](rules/review.md#findings) |
| посмотреть схемы | `tools/doc diagram <файл>` — mermaid-схемы файла отрисованной страницей | [формат схем](rules/diagrams.md) |
| новое R&D | `tools/doc rnd <slug> <тема>`, `tools/doc rnd-check <файл>` — заготовка по шаблону v3.2 и проверка структуры (входит в `check`) | скопировать [шаблон](templates/rnd.md); проверка — ручной путь в [сценарии](skills/doc-rnd.md) |

## Порядок работы с документом

Изменение — это **цепочка документов**, а не пачка правок ([путь изменения](rules/agent-workflow.md)). В каждый момент — один документ:

1. **Место в иерархии.** Тип, вкладка, генерируется ли, где живёт факт (`route`). Цепочка начинается с самого верхнего документа, который меняется по смыслу (значение параметра — в спеке, а не в задаче).
2. **Методология типа.** Читаю только её разделы «Из чего состоит», «Как вести», «Чек-лист». Если она молчит о том, что меняю, ссылается на то, чего нет, или противоречит правильному документу — **сначала обновляю методологию, а за ней инструменты** ([изменение правил](rules/change-process.md#rules-change)).
3. **Правка** одного документа — в источнике факта, не в производном.
4. **Проверка** (`check`).
5. **Следующий документ по графу** (`next`) — по одному; документ, который по смыслу не меняется, дальше не ведёт.

Сценарий целиком — [skills/doc-edit.md](skills/doc-edit.md).

## Договорённости

- **Один документ за раз** — для единичного изменения.
- **Массовые изменения — партиями** ([правило](rules/change-process.md#bulk)): все проверки сразу → коммит состояния → партии исправлений по слою и источнику → связанные документы партией → одна проверка и коммит на партию.
- **Один факт — один источник** ([таблица](rules/change-process.md#single-source)). Значение параметра живёт в одном месте, остальные — ссылкой. Данные — YAML по единице ([порядок](rules/change-process.md#yaml-path)): сначала компактные единицы, полные страницы — одной сборкой в конце пути. Генерируемое руками не правим.
- **Не выдумывать.** Ссылки на решения (`D-N`) и требования (`R-…`) — только существующие (проверь поиском); поля внешней системы или форка — по её коду и спецификации API; не определено — открытый вопрос в спеке.
- **Расхождение нашёл — запиши** в [журнал отклонений](rules/deviations.md): что → почему появилось → правило и проверка. Вне текущей цепочки молча не правь.
- **Замечания и вопросы всегда относятся к спеке.** «Ни к чему не относится» — признак ошибки границ: найди существующее требование.
- **Спеки не генерировать одним шаблоном** — сначала вид спеки ([sdd.md](rules/sdd.md#kinds)).
- **Подтверждения честно:** 🤖 — проверено агентом в роли, 👤 — человеком; агент 👤 не ставит.
- **Экономная проверка ролями** ([правило](rules/approvals.md#economy)): сначала автоматика (`lint` ловит механику до ролей); пачка компонента за все роли (~1–1,5 тыс. токенов на документ); отказ — только блокирующее, с фактом; повторная — только по изменённому.
- **Скрипт, а не LLM:** всё повторяемое — команда, проверка или сценарий; расход замеряется ([журнал](rules/token-costs.md)), расхождение больше 2× — остановиться и разобрать.
- **Ответ по архитектуре:** нарисованная схема нужного вида (mermaid: C1, C2, C3, sequence) + таблица блоков + расширения + плюсы и минусы по каждому модулю + где внесена правка ([формат](rules/diagrams.md#answer)).
- **R&D** — по [методологии](rules/rnd.md): первая страница — ответ на 3 минуты, последствия выбора вносятся по всей цепочке документов.

## Где остановиться и спросить владельца

- нужен выбор продукта; изменение противоречит принятому решению D; удаление; новая вкладка или раздел;
- факт неизвестен и не находится в коде, спецификации API или решениях — открытый вопрос, ниже по цепочке ничего не меняю.

## Безопасность

Не коммитить секреты, `.env`, учётные данные, рантайм-данные (БД, вложения, токены). Файлы вида `*.local*`, `SECRETS*`, `ACCOUNTS*` не читать и не выводить.
