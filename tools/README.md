# Инструменты: doctool и контракт команд

← [README](../README.md) · [AGENTS.md](../AGENTS.md) · [путь изменения](../rules/agent-workflow.md)

Правила сами по себе дороги: агент тратит контекст на чтение всех методологий и всё равно пропускает нужное. Поэтому правило подаётся **в момент правки** инструментом, а проверки — автоматически. Здесь — **doctool** (`tools/doc`): реализация команд, не зависящая от проекта, — всё проектное задаётся в `doc.config.toml` и плагинах. Ниже — установка, конфиг, команды (это же контракт, если пишете свою реализацию), плагины и хуки. Независимая однофайловая проверка ссылок — [mdlinks.py](#mdlinks).

## Установка <a id="install"></a>

1. Скопируйте в проект папку `tools/` (точка входа `tools/doc`, пакет `tools/doctool/`; `tools/doc.cmd` — для `cmd.exe`) и `rules/`; для `rnd` — ещё `templates/`.
2. В корне проекта: `python tools/doc init` — создаст `doc.config.toml` по [шаблону](doctool/doc.config.template.toml); `init --json` — то же в `doc.config.json`.
3. Заполните конфиг ([разделы](#config)): типы документов, генерируемые файлы, граф связей, форматы ID, компоненты, плагины. Добавьте `.doctool/` в `.gitignore` (пакеты проверки, схемы).
4. `python tools/doc check` — до нуля замечаний; затем [хуки](#hooks).

Требования: Python 3.10+, только стандартная библиотека. TOML читается `tomllib` (Python 3.11+; на 3.10 — пакет `tomli`, если установлен), иначе — `doc.config.json`. Файлы данных (компоненты, модель данных) — JSON, TOML или YAML (YAML — если установлен PyYAML). Корень проекта — ближайшая вверх папка с `doc.config.*` (или `--root` / `DOC_ROOT`). Windows: вывод UTF-8, запись с LF, пути с кириллицей. Без конфига работают `route`, `next`, `check` по таблицам `rules/`, но в проект ничего не пишется.

Пример настроенного проекта — [examples/minimal](../examples/minimal/README.md); тесты всех команд на нём — `python -m unittest discover -s tests`.

## Принципы

- **Без копий правил.** Выжимки строятся из таблиц `rules/` при каждом вызове: колонки «Обязательные разделы», «Правила», «Синхронизировать», «Методология» [doc-types.md](../rules/doc-types.md) находятся по имени типа; роли, их вопросы и «кто что подтверждает» — из [approvals.md](../rules/approvals.md). Изменили таблицу — изменился ответ инструмента. В конфиге — раскладка проекта и, если нужно, переопределения. Без `[[types]]` типы и пути берутся из колонки «Где» таблицы типов.
- **Быстро.** `check` — секунды, без сборки сайта, чтобы его можно было звать после каждой правки.
- **Для любого агента.** Команды — обычный CLI; хуки конкретного редактора — тонкая обёртка над `pre` / `post`.
- **Инструменты соответствуют правилам** — это тоже проверка (`check` включает её): методологии из таблицы существуют, пути в сценариях и `AGENTS.md` есть, `route` узнаёт основной путь каждого типа, у узлов графа есть файлы, роли типов описаны.

## Конфиг <a id="config"></a>

| Раздел | Что задаёт | Команды |
|---|---|---|
| `[project]` | `rules_dir` (методологии; может быть вне корня), `command` (как звать инструмент в подсказках), `work_dir` | все |
| `[[types]]` | `name`, `glob`, `exclude`; переопределения `methodology`, `required`, `rules`, `sync`, `source`; `approve` (буквы ролей) или `approve_as` (строка таблицы подтверждений); `sections` (строго), `recommended` (lint), `checklist` (раздел методологии для пакета проверки) | route, next, check, lint, review-pack, approve |
| `[[generated]]` | `glob`, `by` (чем генерируется), `source` (что править), `commit` (можно ли коммитить) | pre, hook-pre, staged, next |
| `[[roles]]` | `letter`, `name`, `question`; пусто — таблица ролей правил | approve, review-pack |
| `[approvals]` | `registry`, `summary`, `skip`, `version_ignore`, `lock_timeout`, `stale_lock`, `sync_on_check` | approve, review-queue, check |
| `[requirements]` | где спеки, формат ID (`id`), заголовок требования, поле задачи, пометки «без задачи», якорь, сценарии, файл открытых вопросов; `[requirements.approvals]` — подтверждение по требованиям (`default`, `by_title`, иначе таблица правил) | check, lint, review-pack, approve |
| `[tasks]` | glob, формат номера, номер из имени файла, раздел требований, пометка «закрыта», колонка компонента, Roadmap и колонка часов в нём; `[tasks.subtasks]` — колонки часов и «готово, когда», диапазон (2–8 ч), строка «Итого»; `[[tasks.derived]]` — производные списки задач | check, lint |
| `[components]` | `list` или `source` (+ `key`) — файл данных; `from_path` — regex «путь → компонент» | lint, finding, review-pack |
| `[findings]` | папка, имя файла, формат ID (`Z-{code}-{n}`: префикс — код компонента) | finding, check |
| `[blocks]` | `glob` карточек (по [шаблону](../templates/block-card.md)) или `source` — файл данных; `fields` — поля, обязательность, `refs` (по какому каталогу ID проверять ссылки); `kinds` — вид блока → раздел | blocks, check, lint |
| `[ids.<вид>]` | каталог ID: `pattern`, `defined_in`, `define` / `define_name`; `check_refs = true` — каждая ссылка в документах должна существовать («не выдумывать D-N») | check |
| `[graph]` | `nodes` (узел → шаблоны путей), `edges` (`[от, к, что проверить]`) | next, hook-post, check |
| `[lint]` | `enable` — встроенные правила | lint |
| `[check]` | `disable`, точки входа, `nav` (навигация сайта — не «сироты»), стили якорей (`github`, `mkdocs`) | check |
| `[rnd]` | папка, шаблон, реестр и формат строки реестра, `check` | rnd, rnd-check, check |
| `plugins`, `builtin_plugins`, `[plugin.<имя>]` | плагины проекта, встроенные плагины, их настройки | все |

## Команды

`tools/doc <команда>` (Windows: `python tools/doc <команда>`). Ручной путь без инструмента — в [AGENTS.md](../AGENTS.md).

| Команда | Вход | Выход | Код возврата |
|---|---|---|---|
| `route <файл>` | путь | тип документа, обязательные разделы, правила, источник факта, методология, что синхронизировать, кто подтверждает; генерируется ли | 0 |
| `pre <файл>` | путь | пусто, если файл не генерируется; иначе — «генерируется <чем>, правь <источник>» в stderr | 2 — файл генерируется (хук запрещает правку) |
| `post <файл>` | путь | выжимка `route` + замечания `check` | 0 |
| `generated <файл>` | путь | «генерируется: <чем>; править: <источник>» или пусто | 0 |
| `next <файл>` | путь | узел графа ([doc-graph.md](../rules/doc-graph.md)) и документы на концах стрелок: шаблоны путей, что проверить, методология каждого; для файла методологии — документы её типов | 0 |
| `check [--only имена]` | — | строгие проверки (имя — префикс замечания): ссылки (`links`), якоря GitHub и MkDocs, `{#id}`, `<a id>` (`anchors`), «сироты» (`orphans`), требование ↔ задача в обе стороны и якоря требований (`trace`), итоги подзадач, Roadmap и производные списки (`tasks`), ссылки карточек блоков (`blocks`), формат и уникальность ID замечаний (`findings`), обязательные разделы типа (`sections`), ссылки на ID существуют (`ids`), структура R&D (`rnd`), инструменты = правила (`tooling`), синхронизация реестра (`approvals`); правила плагинов | 1 — есть замечания |
| `lint [компонент] [--strict]` | — | нестрогие проверки по компонентам: подзадачи с N.M.1, 2–8 ч, «готово, когда» (`subtasks`), чек-лист приёмки (`task-acceptance`), сценарии требований (`requirement-scenarios`), заполненность карточек (`block-card`), экраны «новое» / «доработка» без операции API (`block-screens`), рекомендуемые разделы (`recommended-sections`), заглушки шаблонов (`placeholders`); правила плагинов | 0 — не блокирует коммит (`--strict` — 1) |
| `staged` | индекс git | `check` + запрет коммита генерируемых файлов с `commit = false` | 1 — коммит нельзя |
| `hook-pre`, `hook-post` | JSON хука на stdin | как `pre` / `post` + `next` ([хуки](#hooks)) | 2 / 0 |
| `move <старый> <новый>` | два пути (файл или папка) | `git mv` (без git — переименование); перепись относительных ссылок во всех `.md`, включая исходящие ссылки самого файла, и упоминаний пути в кавычках в `.md` и файлах `[move] extra`; список изменённых файлов | 0 |
| `diagram <файл>` | путь | HTML-страница со всеми блоками ` ```mermaid ` файла (mermaid из CDN) в `.doctool/diagrams/`; выводит её URI | 0 |
| `rnd <slug\|путь.md> <тема>` | slug, тема | файл R&D v3.2 `<[rnd] dir>/<slug>.md` по [шаблону](../templates/rnd.md): тема и дата заполнены, ссылки на методологию и реестр R&D — относительно нового файла; строка в реестре R&D; отказ, если файл есть. Структура сразу проходит `rnd-check`, кроме заглушек источников. Вручную: скопировать шаблон в `rnd/<slug>.md`, заменить `<тема>`, строка в реестре ([новый проект](../rules/structure.md#new-project)) | 0 |
| `rnd-check [файл ...]` | пути (без них — все R&D проекта) | структура R&D v3.2: разделы Э1–Э10, в каждом «**Вывод этапа.**» и ворота G1–G10 ✅ или ⚠️ (у ⚠️ — 📌 и следующий шаг), раздел «Источники» (у строки ссылка, дата — или одна на раздел, уровень А–Г). Входит в `check`. Вручную: команды `grep` в [сценарии R&D](../skills/doc-rnd.md) | 1 — есть замечания |
| `blocks` | — | заполненность карточек блоков: сколько полных, у каких чего нет ([блоки](../rules/blocks.md)) | 0 |
| `review-pack <страница> <буква>` | страница, роль | **один файл** `.doctool/review/…` для проверяющего: тип, вопрос роли, прежнее решение, команда решения, чек-лист методологии типа, требования страницы со сценариями, открытые вопросы их спек, прежние замечания, lint компонента, страница; путь и размер в токенах | 0 |
| `review-queue [буква]` | роль | пары «документ × роль» со статусом ⏳ (после правки — «было ✅ / ❌») | 0 |
| `approve <страница\|ID требования> <буква> ok\|no "<комментарий>" [--human] [--who ИМЯ]` | решение | строка реестра: кто, 🤖 / 👤, дата, ✅ / ❌, версия текста (хеш), комментарий; для ID требования — в `approvals.md` рядом со спекой | 0 |
| `finding <компонент> <ID[,ID]> ok\|wait\|owner\|reject "<что сделано>"` | замечания | статус ✅ / ⏳ / 📌 / «отклонено» в файле замечаний компонента ([ревью](../rules/review.md#findings)) | 0 |
| `finding <компонент> next-id` | компонент | следующий свободный ID (`Z-<код>-<N>`) | 0 |
| `init [--json] [--force]` | — | шаблон конфига в текущей папке (или `--root`) | 0 |
| `plugins` | — | загруженные плагины, их правила, каталоги ID и команды | 0 |

Синхронизация реестра подтверждений (в `check`, `approve`, `review-queue`): строки ⏳ для обязательных пар «документ × роль» по типу документа; сброс решения в ⏳ с пометкой «текст изменён после решения «✅» от …», если хеш текста изменился (различия в пробелах не в счёт; `version_ignore` — что ещё не в счёт); удаление строк удалённых документов; сводная таблица с «⏳ было ✅ / ❌». Запись реестра — под файловой блокировкой `<реестр>.lock`: параллельные проверяющие не теряют строк; занятая дольше `lock_timeout` — ошибка, брошенная (старше `stale_lock`) — снимается.

## Плагины <a id="plugins"></a>

Проверки, которые зависят от устройства проекта (модель данных, OpenAPI форка, схема БД), — не в ядре, а в плагинах. Плагин — модуль Python: встроенные лежат в `tools/doctool/plugins/` и включаются `builtin_plugins = ["datamodel"]`, плагины проекта — папки или файлы из `plugins = ["tools/doc_plugins"]` (ключи верхнего уровня — до первой `[таблицы]` конфига).

```python
from doctool.api import lint_rule, check_rule, command, ref_kind, util as U

@check_rule("purpose")                             # строгое: yield сообщение → check вернёт 1
def purpose(ctx):
    for f in ctx.spec_files():
        if len(U.plain(U.section(ctx.text(f), "Purpose"))) < 50:
            yield f"{f}: Purpose короче 50 символов"

@lint_rule("agent-estimate")                       # нестрогое: yield (компонент, сообщение)
def estimate(ctx): ...

@command("tasks-table", "сгенерировать TASKS.md")  # новая команда tools/doc tasks-table; вернуть код
def tasks_table(ctx, args): ...

@ref_kind("table")                                 # каталог ID для refs карточек: вернуть (regex, множество ID)
def tables(ctx): ...
```

`ctx` — контекст проекта: `ctx.get("plugin.<имя>.<ключ>")`, `ctx.glob(...)`, `ctx.text(путь)`, `ctx.types()`, `ctx.type_of(путь)`, `ctx.requirements()`, `ctx.tasks()`, `ctx.blocks()`, `ctx.components()`, `ctx.component_of(путь)`, `ctx.ids(вид)`. Примеры: встроенный [datamodel](doctool/plugins/datamodel.py) (таблицы и интерфейсы из файла данных: ссылки карточек, I-коды спек, «таблица названа в задаче компонента») и плагин проекта [house.py](../examples/minimal/tools/doc_plugins/house.py).

## Хуки <a id="hooks"></a>

| Где | Что вызывает |
|---|---|
| До правки файла (хук редактора, например Claude Code `PreToolUse` на Edit / Write) | `hook-pre` (или `pre <файл>`); код 2 — правка генерируемого файла запрещена, агенту называется источник |
| После правки (хук `PostToolUse`) | `hook-post` (или `post <файл>` и `next <файл>`) → в разговор агента: выжимка правил, следующие документы, замечания проверок |
| git `pre-commit` | `staged` |

Пример для Claude Code (`.claude/settings.json`):

```json
{
  "hooks": {
    "PreToolUse": [{ "matcher": "Edit|Write", "hooks": [{ "type": "command", "command": "python tools/doc hook-pre" }] }],
    "PostToolUse": [{ "matcher": "Edit|Write", "hooks": [{ "type": "command", "command": "python tools/doc hook-post" }] }]
  }
}
```

`hook-pre` / `hook-post` читают JSON хука из stdin (путь файла — `tool_input.file_path`, также `notebook_path` или `path`) и делают то же, что `pre` / `post`; `hook-post` возвращает текст в `hookSpecificOutput.additionalContext` (до 15 замечаний). Другие агенты зовут `pre` / `post` / `next` напрямую. git-хук `.git/hooks/pre-commit`: `#!/bin/sh` и `exec python tools/doc staged`.

## mdlinks.py — независимая проверка ссылок <a id="mdlinks"></a>

```bash
python tools/mdlinks.py [корень] [--entry README.md --entry AGENTS.md ...] [--no-orphans] [--no-anchors]
```

Проверяет все `*.md` под корнем (кроме `.git`, `node_modules`, `.venv`, `site`, `build`, `dist`):

- **битые относительные ссылки** `[текст](путь)` и `[текст](путь#якорь)` — файл или папка не существует;
- **битые якоря** — в целевом файле нет заголовка с таким GitHub-slug, явного `<a id="…">` / `id="…"` или `{#…}`;
- **«сироты»** — Markdown-файлы, на которые не ведёт ни одна ссылка из других файлов (кроме точек входа: по умолчанию `README.md`, `AGENTS.md`, `CLAUDE.md` в корне и `README.md` в любой папке).

Внешние ссылки (`http:`, `https:`, `mailto:`), ссылки-заглушки шаблонов вида `(<путь>)` и ссылки внутри блоков кода не проверяются. Код возврата 1 при замечаниях. Зависимостей нет (Python 3.8+). То же, с настройкой и стилем якорей MkDocs, — `tools/doc check --only links,anchors,orphans`.
